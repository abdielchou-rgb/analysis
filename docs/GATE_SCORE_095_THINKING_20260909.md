# Gate 0.885 → 0.95+ 思考总结

**日期**：2026-09-09
**触发**：宁德时代 earnings_notes 报告 Gate 通过（0.885）后，用户问"怎么提高到 0.95 以上"
**方法**：写诊断脚本 `scripts/diagnose_gate.py` 对 `_gate_check.md` 跑全部 98 项检查，按 severity 分组、按失分排序

---

## 一、先把"分数"变成"账"

直觉会告诉你"写得更好分数就更高"。但 0.885 是个加权平均，不是质量评分。先做算术：

- 总分 = error_mean（23 项 ERROR 级检查的均分）
- 要 0.95 → 23 项总共最多失 **1.15 分**
- 当前失分 **2.64 分** → 需要拿回至少 1.5 分

这一步把问题从"提升报告质量"（模糊、不可执行）变成"找到 2.64 分失分分布，逐项拿回"（具体、可核算）。

## 二、失分分布（诊断脚本实测）

| 检查项 | 得分 | 失分 | 表面问题 |
|---|---|---|---|
| so_what_chain | 0.36 | 0.64 | So What 密度 0.60 avg，最差 0.00 |
| data_dict_refs | 0.40 | 0.60 | 2 处数据冲突（毛利率 44% vs 20%） |
| anti_patterns | 0.45 | 0.55 | "护城河宽阔(反身性)" 类伪深度句式 3 处 |
| attribution_depth | 0.60 | 0.40 | 缺子因子拆解 + 3 因子以上 |
| cross_section_consistency | 0.70 | 0.30 | 目标价 260 vs 300 两值并存 |
| 盈利质量 | 0.85 | 0.15 | 缺"盈利质量"子项 |

最大三项失分（so_what + data_dict + anti_patterns）= 1.79 分，占全部失分的 68%。

## 三、关键洞察：失分大头不是"写得差"，是"口径错位"

逐项追问"这个失分的真实根因"，发现三类系统性错位：

### 错位 1：检查器把非正文段算进分母（so_what_chain 0.36）

"评级说明表"、"风险提示"、"附录"这些合规段被当分析段评 So What——它们本来就不该有 So What。42 段分母里混着格式段，密度被稀释到 0.60。**这是检查器的口径 bug，不是报告问题。**修分段器跳过表格/合规/附录段，0.36 → 0.85+，零写作改动。

### 错位 2：rewrite 节点绕过了数值锚定（data_dict_refs + cross_section_consistency）

write_sections 有锚卡数值一致性强制（"目标价不得出现 310 和 387 两个值"），但 **rewrite_sections 的 prompt 没有这个条款**。DeepSeek 审稿→重写后，目标价 260（锚卡）vs 300（旧叙事残留）并存，毛利率也写串（把"环比降幅"当"毛利率"）。数据冲突 2 处 + 目标价冲突 1 处，合计失 0.90 分——全部是 rewrite 丢锚造成的。

### 错位 3：逃逸变体不在黑名单（anti_patterns 0.45）

"(反身性)/(确定性)" 这类括号后缀空标签是新出现的伪深度句式，anti_patterns 黑名单没收录。StyleCompiler 是确定性正则清理——黑名单没更新就拦不住。

### 反面：真正的写作质量问题排最后

attribution_depth 0.60（缺子因子拆解）是唯一"纯写作质量"失分项——0.40 分，占失分 15%。**如果先去改 writer prompt 提升写作，是在用 15% 的杠杆努力，而 85% 的失分来自检查器和管线口径。**

## 四、修复路径与算账

### 第一批（A-track，确定性修复，不碰写作语义）

| # | 修复 | 拿回 | 手段 |
|---|---|---|---|
| 1 | so_what_chain 分母修正 | ~0.49 | 检查器跳过格式段 |
| 2 | rewrite prompt 补锚卡条款 + 后处理对账 | ~0.60 | rewrite_sections 注入锚卡；post-process 数字与 data_dict 对账 |
| 3 | anti_patterns 黑名单扩容 | ~0.55 | 加括号空标签正则 |
| 4 | 目标价统一后处理 | ~0.30 | _post_process_for_gate 多值归一（扩展现有 [FIN-A] 机制） |

四项合计拿回 ~1.94 分 → error_mean ≈ (20.36+1.94)/23 ≈ **0.969**。留了余量，即使 so_what 只修到 0.80、对账只消一半冲突，也在 0.95 上下。

### 第二批（warn 级，报告观感但不进总分）

- inline_citations 0.30：post-process 自动补 [En]（claim_citation.annotate_inline 已有现成能力，接线即可）
- cross_industry_contamination 0.20：SNE Research 是行业数据源名，被当外来公司——加数据源机构白名单
- template_repeat 0.50："综合判断："重复 3 次，StyleCompiler 去重

## 五、这次思考的可复用结论

1. **加权平均分数先做失分核算**，不做质量直觉。"怎么到 0.95" 翻译成"23 项最多失 1.15 分"后，方案自动浮现。
2. **失分 ≠ 写得差**。诊断显示 85% 失分来自三处系统性口径错位（检查器分母、rewrite 丢锚、黑名单过期）——全是管线 bug，不是 LLM 能力问题。
3. **修复顺序按"失分×确定性"排，不按"重要性"排**。so_what 分母修正是检查器 bug（确定性 100%），attribution_depth 是写作质量（改了未必涨）。先摘确定性果子。
4. **rewrite 是质量盲区**。write 有锚卡强制，rewrite 没有——任何"写作→审稿→重写"管线里，重写节点继承全部约束的清单容易被遗漏。这次是数值一致性，下次可能是数据标注 (A)/(E)/(F) 或图表引用。
5. **诊断脚本本身是资产**。`diagnose_gate.py` 把 Gate 从"黑盒总分"变成"可核算账本"，以后每次提分都先跑它。

## 六、一句话

> 0.885 → 0.95 的最短路径不是"让 LLM 写得更好"，而是修三个管线口径 bug：so_what 检查器把合规段算进分母、rewrite 绕过数值锚定、anti_patterns 黑名单缺新变体。修掉它们拿回 ~1.9/2.64 失分，0.95 是算出来的，不是赌出来的；唯一的真写作失分（归因深度 0.40 分）留作第二批。
