## 阶段总览（依赖关系）

```
P0 地基  修 priority bug + 版本管理 + 门禁熔断 + 基线  ← 一切的地基
  ↓
P1 供能  三通道 + L0 吸收 + 缓存前缀 + Marvis 预取       ← 省 token 主力
  ↓
P2 切组  内容包预检 + 合并层重写 + 影响传播 + 弹性预算   ← 质量与收敛
  ↓
P3 圆桌  OpenRouter 异源终审 + 成本日志 + 信誉机制       ← 收尾增强
```

**依赖关键**：P2 的"影响传播"依赖 P0 的"版本管理"；P1 的"三通道"依赖 P0 的"priority 修复"。故 P0 必须完整交付后才进入 P1。

## P0：地基（预计 1-2 天）

### P0-1 修复 agent_provider priority 语义反转【P0，最高优先】
```
现状：core/agent_provider.py priority=-1（注释"兜底"但注册表升序取最小 → 实际最高优先级）
动作：
  1. AgentProvider priority: -1 → 10（显式枚举：PRIMARY=0 / FALLBACK=50 / LAST=100）
  2. 单元测试锁定：provider="auto" 时 agent_provider 必须排在 deepseek 之后
  3. 同步修正 deepseek_client.py 底部"priority=99"过时注释
验收：pytest 新测试通过；provider 排序正确
```

### P0-2 模块版本管理地基【P0，逻辑倒置修正项】
```
现状：无模块版本概念；全量重写是 R79-R87 token 黑洞的根因
动作：
  1. 新增 core/module_version.py：每个模块（SAC 维度/章节/论点单元）独立版本单元
     - version_id / content / hash / parent / frozen_facts / timestamp / status
  2. 写盘位置：工作区 10_draft/<module>/v{n}.json（保留历史可回滚）
  3. 提供接口：checkout(latest) / rollback(v_prev) / mark_dirty(module)
验收：单测覆盖 版本创建/回滚/脏标记
```

### P0-3 门禁熔断（防局部修复死锁）【P0，圆桌批判 F3】
```
现状：fail-fast 若拦 80% 内容 → 无限局部修复循环（新的 300s 空等）
动作：
  1. write_revise_loop 加计数：同一模块局部修复 N 次（默认 3）仍失败
     → 降级为该模块全量重写（不无限循环）
  2. 熔断事件写日志 + 决策审计报告
验收：单测模拟连续失败 → 第 3 次触发全量重写
```

### P0-4 基线测量【P0，验收锚点】
```
现状：无基线，验收"降 50%"无参照
动作：
  1. 写 scripts/bench_baseline.py：跑一篇标准 listed_company
     → 记录 各阶段耗时 / 各节点 token / Gate 轮次 / 全量重写次数
  2. 基线数据落 benchmark/baseline_20260807.json
验收：基线文件产出，作为 P0/P1/P2 验收对照
```

### P0-5 工作区隔离 + 根目录卫生【P0.5，低成本高收益】
```
现状：产物混在 output/ + 根目录（30+ gate_*.txt 调试残留）
动作：
  1. 每报告建独立工作区：00_input/ 10_draft/ 20_output/ 90_temp/ + WRITING_CONTRACT.md
  2. 清理根目录调试残留（gate_*.txt/fixgate*.py/sacdump*）→ archive/
  3. 工作区规范写进 docs/CLAUDE-architecture.md
验收：根目录零调试残留；新报告产物在工作区
```

**P0 验收**：priority 测试绿 + 版本管理单测绿 + 熔断单测绿 + 基线文件产出 + 根目录干净

## P1：供能——省 token 主力（预计 3-5 天）

### P1-1 三通道路由（ProviderRegistry 接线）【P1】
```
动作：
  1. 按《三资源最优配置方案》注册 deepseek(P0)/openrouter(P1)/agent_provider(P2)
  2. LLM_PROVIDER=deepseek 为主模式；per-node model routing（L1 chat / L2 reasoner）
  3. 降级矩阵：DeepSeek 熔断 → OpenRouter（不自动回 Marvis）
  4. 超时：DeepSeek 60-90s / OpenRouter 90-120s / Marvis 120s
验收：provider 排序正确；DeepSeek 挂时降级 OpenRouter 可工作
```

### P1-2 L0 Python 吸收【P1，0 token 大项】
```
动作：盘点现有 LLM 调用，能规则化的全转 Python
  - 数字校验/口径统一（data_caliber 已有）→ 100% L0
  - 图表生成（chart_runner 已有）→ 100% L0
  - 排版/格式（format_sheriff 已有）→ 100% L0
  - 相似度/重复检测（template_blacklist 已有）→ 100% L0
  - 评分（score_text）→ 若规则可判定则 L0，否则 L1
验收：KPI 表（每类任务 L0/L1/L2 分流占比）+ token 对比
```

### P1-3 Prompt Caching 前缀【P1，收益最大】
```
动作：
  1. 宪章 + 大纲 + 事实库 拼成固定前缀，所有节点共享
  2. DeepSeek 自动磁盘缓存实测命中率与成本（口径与 Anthropic 不同，实测为准）
  3. 缓存失效策略：大纲/事实变更 → 前缀版本+1
验收：实测长文档缓存命中率 > 60%，前缀 token 成本 -80%
```

### P1-4 Marvis 免费预取通道【P1，零等待】
```
动作：
  1. 主链跑 DeepSeek 时，后台并行派 Marvis 免费通道产候选草稿
  2. channel=marvis 显式标记，落候选区（10_draft/candidates/）
  3. 失败即弃（不依赖）；候选过 verifier 才能被选用
验收：主链不受 Marvis 影响；候选可用率（过 verifier）> 30%
```

**P1 验收**：三通道降级可工作 + L0 吸收 KPI 表 + 缓存命中 >60% + Marvis 候选过 verifier >30%

## P2：切组——质量与收敛（预计 1-2 周）

### P2-1 内容包预检（防空维硬写）【P2，F2 仲裁规则】
```
动作：
  1. 写前统计每 SAC 维度数据充足度（复用 data_sufficiency 打分）
  2. 仲裁规则：充足度 <0.5 降级（诚实留白）/ 0.5-0.8 精简 / >0.8 全写
  3. 大纲为内容让路（内容不够就合并维度，不硬写）
验收：空维报告不再出现"无数据硬写"；Gate 无"数据不足"类失败
```

### P2-2 合并层重写（带证据链）【P2，组装最大坑】
```
现状：_editor_merge 只传摘要（ACL 2025 反例）
动作：
  1. 合并传"摘要 + 关键证据引用 + 可回溯指针"
  2. 每层合并注入三类锚：大纲锚（位置）/事实锚（共享数字）/风格锚（宪章）
  3. 每层轻量校验（覆盖度/衔接度/一致度），fail-fast
验收：合并层输出带证据链；全文数字/口径统一（data_caliber 通过）
```

### P2-3 影响范围传播【P2，依赖 P0-2 版本管理】
```
动作：
  1. 模块依赖图：input_contract → 记录"谁依赖我"
  2. 模块替换后 → 下游标记"待重校验"，级联重算受影响子树
  3. 与 P0-3 熔断联动：级联重算也有上限（防雪崩）
验收：改 A 模块 → B/C 自动标记重校验；无全量重写
```

### P2-4 论点单元级并行【P2，细化切分】
```
动作：
  1. dimension_grouper 由段级并行 → 论点单元级（200-500 字）并行
  2. 无依赖论点单元并行；有依赖等上游
验收：并行度提升；单篇墙钟时间较基线降 40%+
```

**P2 验收**：空维不硬写 + 合并带证据链 + 影响传播可工作 + 并行度提升

## P3：圆桌与增强（预计 1 周）

### P3-1 OpenRouter 异源终局圆桌【P3】
```
动作：
  1. 终稿评审走 OpenRouter 异源模型（2-3 家：qwen/turbo 等），与 DeepSeek 不同源
  2. 至少 1 席付费模型；评审输出结构化（维度打分 + 问题定位 + 修复建议）
验收：评审通过的报告 Gate 全绿；圆桌反馈可定位到段落
```

### P3-2 成本日志 + 审计【P3】
```
动作：
  1. observability.db 扩展：每节点 token/模型/耗时/通道
  2. 交付附"成本审计报告"（这篇花了多少钱、哪里最贵）
验收：每篇报告成本可查；TOP 成本节点可见
```

### P3-3 圆桌信誉机制【P3，I3 激励倒挂修正】
```
动作：
  1. 圆桌评审过的报告 30 天后回测（prediction_loop 已有）
  2. 错误计入评审者信誉分；信誉分影响下次评审权重
验收：信誉分机制上线；评审者历史错误可查
```

### P3-4 golden dataset 验证局部修复【P3，F4 成本分布证据】
```
动作：
  1. 抽样 10 篇报告，对比"全量重写 vs 局部修复"的 token 与质量
  2. 数据落 benchmark/；用数据定最终策略（局部修复 or 混合）
验收：局部修复 vs 全量重写的成本分布报告产出
```

**P3 验收**：异源圆桌接入 + 成本日志可查 + 信誉机制上线 + 局部修复成本分布报告
