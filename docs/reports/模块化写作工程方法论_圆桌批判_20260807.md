## 第一部分 完整工程方法论

### 总纲

**一句话**：骨架冻结、内容生长、锚定收敛、按需修复、三通道供能、宪法守门。

**目标函数**（三个，可量化的验收）：

```
更快：单篇墙钟时间 < 现状 50%（先跑基线再定 target）
更好：Gate 迭代轮次 ≤ 2；无全量重写；事实矛盾拦截率 100%
更省：长文档 token 成本 < 现状 40%（先实测再定 target）
```

### 五层架构

```
┌─────────────────────────────────────────────┐
│ L5 宪法层   FP1-FP8 + CLAUDE.md（不可绕过的边界）│
├─────────────────────────────────────────────┤
│ L4 门禁层   IronGate + 每层 verifier + 终局圆桌  │
├─────────────────────────────────────────────┤
│ L3 供能层   DeepSeek P0 / OpenRouter P1 / Marvis P2（L0/L1/L2 分级）│
├─────────────────────────────────────────────┤
│ L2 组装层   content包→论点单元→5-8收敛→三类锚    │
├─────────────────────────────────────────────┤
│ L1 切分层   STORM 大纲 + 事实单元聚簇 + 数据契约  │
└─────────────────────────────────────────────┘
```

---

### 模块 1：切（Decomposition）

```
输入：主题 + 委托方要求
步骤：
  1. 多视角调研（STORM 式）→ 大纲草案（SAC 26 维为基础骨架）
  2. 内容包预检：统计每维数据充足度 → 空维降级/合并，实维保留
     （防空维硬写——幻觉第一来源）
  3. 事实单元抽取（带来源）→ 聚簇 → 映射到大纲
  4. 冻结大纲 + 每个模块定义数据契约：
       input_contract  依赖的上游数据/结论
       output_contract 产出 + 对外承诺的事实点
       frozen_facts    本模块锚定的不可变事实（数字/口径/引用）
输出：冻结大纲 + N 个模块契约（N 由内容量定，不按字数拍）
```

### 模块 2：写（Parallel Generation）

```
  1. 论点单元级并行（200-500 字，claim+evidence+reasoning 自洽）
  2. 无依赖模块并行（DIM_PARALLEL），有依赖必须等上游
  3. 每模块任务自带：大纲锚 + 事实锚 + 风格锚（写作宪章）
  4. 模块写时即校验（fail-fast verifier）：
     小错 → Self-Refine 精炼（版本+1）
     大错 → 丢弃重建（版本+1）
  5. 规模分级：简单 8-12 模块 / 复杂 40+（防过度工程）
```

### 模块 3：组（Assembly）

```
  1. 自底向上逐层收敛：论点单元 → 子章节（5-8 一组）→ 章节 → 全文
  2. 每层合并必须带源上下文：摘要 + 关键证据引用 + 可回溯指针
     （严禁只传摘要——ACL 2025 反例正解）
  3. 每层注入三类锚：大纲锚（位置）/ 事实锚（共享数字）/ 风格锚（宪章）
  4. 每层轻量校验（覆盖度/衔接度/一致度），fail-fast
  5. 全文完成 → 终局圆桌（事实核查官/逻辑审计官/读者代表/领域专家/对抗者）
```

### 模块 4：修（Local Repair）

```
  模块版本管理（v1/v2/v3 保留历史可回滚）
  出错 → 定位器精确归因（段落级，复用 R83 问题覆盖率经验）
  ├─ 小错 → Self-Refine 精炼
  ├─ 大错 → 丢弃重建
  └─ 深度不够 → 补子模块（保留骨架，父模块只重写过渡段）
  替换后 → 影响范围传播：依赖本模块的下游标记"待重校验"
  崩溃 → checkpoint 回滚（write_checkpoint 已有）
```

### 模块 5：供能（Energy - 三通道）

```
  DeepSeek  P0 主力   L1 chat / L2 reasoner，实时关键链，并发 3-5
  OpenRouter P1 兜底  降级 + 终局圆桌异源（至少 1 席付费）
  Marvis    P2 免费  后台异步预取草稿（失败即弃，绝不进终稿合并层）
  L0        能 Python 的 Python（0 token：查表/正则/格式/评分）
  Prompt Caching：宪章/大纲/事实库做缓存前缀（DeepSeek 口径实测）
```

### 模块 6：守门（Governance）

```
  1. IronGate（已有，保留）→ 升级为"模块级 verifier + 终局圆桌"双门禁
  2. 出口指纹（已有）→ 只有完整跑完才导出
  3. 数据兜底（第〇原则）→ 三通道落地后数据兜底同样分级（L1 提取/L2 校验）
  4. 成本日志（observability.db 扩展）→ 每节点 token/模型/耗时，随审计报告
  5. 决策审计（一次性授权协议 CLI 化）→ 启动问卷锁硬决策点，交付附审计
```

### 分阶段实施

| 阶段 | 内容 | 验收 |
|------|------|------|
| P0.5 | 工作区隔离 + 根目录卫生清理 | 根目录零调试残留 |
| P0 | 修 priority bug + 跑基线 + 超时下调 | 基线测出，单篇耗时降 50% |
| P1 | 三通道 + L0/L1/L2 + 启动问卷 CLI 化 + 弹性预算 | token 降 40%，免费通道过 verifier |
| P2 | 模块版本管理 + 影响传播 + 合并层重写（带证据链）+ 内容包预检 | Gate 轮次 ≤2，无全量重写 |
| P3 | 圆桌终局异源 + 成本日志 + 按需分解 | 审计可查，异源评审接入 |

## 第二部分 圆桌批判（多角色找缺陷）

> 规则：各角色先独立给出最尖锐的质疑，再交叉确认。

### 圆桌一：Feynman——术语泡沫检视

**质疑 1："自底向上让内容长出来"是否只是把名词换了个说法？**
- 我能不能用一个具体例子讲清楚"事实单元→内容包→大纲"？
- 不能。STORM 和 ConvergeWriter 是论文原型，2hao 的 SAC 26 维是**多年沉淀的行业骨架**。两者如何融合，方案只有方向没有机制——"内容包预检"具体怎么算"数据充足度"，数据接口是什么，全是空白。
- **验证**：做不出来实验 = 没理解。本文方法论的"模块 1"没有落到可运行的伪代码，是术语泡沫。

**质疑 2："证据驱动"与"大纲驱动"到底谁主导？**
- 方案说"分时复用"，但没定义切换条件。大纲和内容冲突时（大纲要 5 维，内容只够 3 维），谁让步？切换规则缺失 = 执行时必然二义。

### 圆桌二：Taleb——反脆弱检视

**质疑 3：最坏情况是否会出局？**
- 三通道全挂（DeepSeek 熔断 + OpenRouter 限流 + Marvis 无 responder）→ 退回单 provider 时代 → 其实不会出局，会退化。**但**：如果"模块级 verifier"在写时即拦、把 80% 内容判定为不合格 → 整篇卡在局部修复循环 → 这才是新的"300s 空等"形态——**门禁过严会导致系统性死锁**。
- **遍历性**：重复一万次（跑 1000 篇报告），"局部修复"的 token 成本分布如何？如果每篇都有 20% 模块触发影响传播、级联重算，平均成本可能反而高于全量重写。方案没有给出局部修复优于全量重写的**经验分布**，只有假设。

**质疑 4：谁承担错误后果？（skin in the game）**
- "终局圆桌至少 1 席付费"——但圆桌评审者不承担报告出错的后果。**评审的激励是"看起来对"，不是"真的对"**（R47 已教训）。没有"评审错了被追责"的机制，圆桌只会越来越宽松。

### 圆桌三：工程师——可落地性检视

**质疑 5：这是 6 个新系统，不是一个升级。**
- 三通道路由、模块版本管理、影响传播、合并层重写、内容包预检、成本日志——每一个都是中型项目。方案没排依赖关系，没评估"哪个是其他一切的阻塞点"。**版本管理是所有一切的地基，但被排在 P2**——逻辑倒置。

**质疑 6：测试策略缺失。**
- 2hao 有 143+ 回归测试。模块化重构会让所有测试要改。方案没说：现有测试如何适配？golden dataset 如何重建？**重构最怕的"改到一半测试全红"没有应急预案。**

### 圆桌四：产品——用户视角检视

**质疑 7：更快更好更省，但"更稳"呢？**
- 用户要的是**能信任的终稿**，不是最快的稿。方案把大量笔墨给速度/成本，对"如何证明这稿是对的"笔墨不足。**可信度 = 来源可回溯 + 结论可验证**——方案只在"合并层带指针"提了一嘴，没有端到端"每个结论可点回数据"的可视化承诺。

### 圆桌交叉确认：最大共识缺陷

**三票以上共同指向的缺陷：**

| 缺陷 | 票数 | 本质 |
|------|------|------|
| **版本管理是地基却排在 P2** | Feynman/工程师/产品 | 没有版本管理，局部修复/影响传播/回滚全是空谈，它是 P0 不是 P2 |
| **大纲与内容冲突的切换规则缺失** | Feynman/产品 | 方案有两套逻辑（STORM 骨架 vs ConvergeWriter 生长），没定义仲裁 |
| **局部修复无成本分布证据** | Taleb/工程师 | 可能级联重算比全量重写更贵，需要 golden dataset 验证 |
| **门禁过严→局部修复死锁** | Taleb/工程师 | fail-fast 拦 80% → 死循环，需要熔断：N 次修复失败→降级全量重写 |
| **圆桌激励倒挂未解** | Taleb/产品 | 评审不担责→评审宽松，需"错误追责"机制 |

## 第三部分 缺陷清单与修订建议

### 致命缺陷（不修不能动手）

| # | 缺陷 | 修订 |
|---|------|------|
| F1 | 版本管理排 P2，逻辑倒置 | **版本管理提前到 P0**（与 priority bug 同批），它是一切局部修复的地基 |
| F2 | 大纲与内容冲突无仲裁规则 | 定义仲裁：**内容充足度优先**——数据只够 3 维就写 3 维，大纲为内容让路；SAC 维度降级走"诚实留白"而非硬写 |
| F3 | 门禁过严→修复死锁 | 加熔断：**同一模块局部修复 N 次（建议 3）仍失败 → 降级全量重写该模块**，防死循环 |
| F4 | 局部修复无成本分布证据 | 建 golden dataset：抽样 10 篇报告，对比"全量重写 vs 局部修复"的 token 与质量，用数据定策略 |

### 重要缺陷（P1 修）

| # | 缺陷 | 修订 |
|---|------|------|
| I1 | 测试策略缺失 | 模块化重构同时维护 143 回归；golden dataset 重建进计划；"改到半路测试全红"用 feature flag 隔离 |
| I2 | 数据充足度判定无机制 | 复用 `data_sufficiency` 已有打分，定义阈值：<0.5 降级、0.5-0.8 精简、>0.8 全写 |
| I3 | 圆桌激励倒挂 | 圆桌输出与历史报告错误挂钩：评审过的报告 30 天后回测错误，计入评审者信誉分 |
| I4 | 可信度承诺不足 | 终稿附"结论→数据→来源"三层可回溯链接（evidence_chain 强化），作为交付物的一部分 |

### 可选优化（P2/P3）

| # | 优化 |
|---|------|
| O1 | 三通道降级矩阵表（触发条件/超时/用户可见信号） |
| O2 | 并发写 SQLite 压力测试（WAL 已启用，但并发写入需验证） |
| O3 | 成本预算口径：项目级 vs 每报告级，定义上限与报警 |
| O4 | 工作区隔离后接 subdirectory 级约定（目录触碰才加载） |

## 第四部分 结论

**方法论整体成立**，但圆桌批判暴露了四个致命缺陷，**其中最重要的是 F1（版本管理排位错误）和 F3（门禁死锁风险）**——这两个不修，整个"模块化"大厦会建在沙子上。

**修订后的正确顺序**：

```
P0  修 priority bug + 版本管理地基 + 门禁熔断 + 跑基线
P1  三通道 + 内容包预检（仲裁规则）+ 合并层重写 + 弹性预算
P2  影响传播 + 终局圆桌 + 成本日志 + golden dataset 验证局部修复
P3  圆桌信誉机制 + 可信度可视化 + 工作区 subdirectory 约定
```

**一句话**：模块化写作是正确方向，但"局部修复"是最大不确定项——在 golden dataset 证明它之前，别把赌注全押上；先做版本管理这个地基，再谈省 token。
