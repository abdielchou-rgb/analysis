# 2号分析师架构升级思考：Skill + Subagent + Python

> 日期：2026-08-08
> 触发：用户问"要不要升级成 skill+subagent+Python 架构"
> 方法：综合整个会话实战（油位14版迭代、工作台/管线双轨、三轮圆桌、144个Python引擎）判断
> 结论先行：**要升级，但不是推翻——是"分层"：Python 管确定性（数据/计算/校验/门禁），Subagent 管并行深度（研究/多角色评审），Skill 管能力打包（方法论/框架/写作姿态）。三者不是替代，是各司其职。**

---

## 一、先看现状：2hao 现在是什么

```
当前 2hao = 纯 Python 管线架构
├── core/ 144 个引擎（数据采集/计算/校验/门禁/知识库）
├── pipeline/ 编排（E2E + section_writer + iron_gate）
├── 工作台路径（intent_parser + context_compiler + verify_report）
└── 无 skills / 无 agents 目录

实战证明：
✅ Python 引擎是"事实基础"（财务复算/口径检测/门禁全绿）——Marvis 圆桌认可"每算必验"
✅ 门禁体系有效（business_logic/relation/metacomment/docx完整性 9项校验）
❌ 但"写作质量"依赖单 Agent 一次性生成 → 油位14版迭代证明：单 Agent 反复改会引入 AI 痕迹
❌ 圆桌评审要手动触发 → 没有自动化的"多角色批判"环节
```

---

## 二、为什么升级（3 个实战痛点）

### 痛点1：单 Agent 写作的"质量天花板"
油位 14 版迭代的最大教训：**单 Agent 反复 patch 会不断引入元评论语言/版本迭代说明**（"建议验证""而非外部""见3.2"）。这不是我笨，是单 Agent 没有"外部批判视角"——自己写自己改，天然缺对抗。

**Subagent 解法**：写完后派独立 Subagent 做"多角色评审"（投行/MBB/审计），与写作 Agent 隔离，天然对抗。Marvis 三轮圆桌已经证明这个有效——我写的，它评的，互补。

### 痛点2：框架/方法论没打包，靠"记性"
2hao 有 26 维 SAC、14 个框架、6 套方法论，但**都在 Python 里，没打包成"可调用技能"**。每次写报告，要么靠我读框架代码，要么靠 context_compiler 注入——既不标准也不完整（油位 v4.6 才发现漏了波特五力）。

**Skill 解法**：把"产业生命周期分析""波特五力评估""利润池分析""决策备忘录写作"打包成 skill——每个 skill 自带方法论 + 触发条件 + 检查清单。写行业报告自动加载对应 skill，不用靠记性。

### 痛点3：并行深度不足
油位调研（竞对/宏观/上游）是我串行 WebSearch 的，慢且浅。Subagent 可以并行派 3-5 个研究任务（竞对/政策/供应链/财务），每个深度独立。

---

## 三、目标架构：三层分工

```
┌─────────────────────────────────────────────────┐
│ Layer 1: Python（地基，不动）                      │
│   144 引擎 + 管线 + 门禁体系                       │
│   职责：确定性计算/数据采集/校验/门禁/导出           │
│   "能 Python 的 Python"——0 token，可复现，已证明    │
├─────────────────────────────────────────────────┤
│ Layer 2: Subagent（并行层，新增）                  │
│   研究型：并行派 3-5 个调研 agent（竞对/政策/上游/财务）│
│   评审型：写完派独立多角色评审 agent（投行/MBB/审计）  │
│   职责：不可确定性的深度工作（研究/批判）             │
│   "并行 + 隔离 + 对抗"——解决单 Agent 质量天花板     │
├─────────────────────────────────────────────────┤
│ Layer 3: Skill（能力层，新增）                     │
│   方法论打包：生命周期/波特五力/利润池/决策备忘录      │
│   写作姿态打包：作者姿态/去AI化/框架检查清单          │
│   职责：标准能力复用，不靠记性                      │
│   "按任务加载技能"——Progressive Disclosure         │
└─────────────────────────────────────────────────┘
```

**关键设计原则**：

1. **Python 是地基，不是被替换**——财务复算/门禁/口径检测全部留 Python（Marvis 认可"每算必验"）。升级是"加层"，不是"重构"。

2. **Subagent 只做"不可确定性"的工作**——研究（调研/收集）、评审（批判/多角色）、探索（open-ended）。不做确定性计算（那是 Python 的）。

3. **Skill 是"方法论接口"**——把"分析框架""写作规范"从代码/记性中解放，变成可加载的能力包。

---

## 四、落地路径（分3期）

### 一期：Skill 化（最快见效，1-2天）
把已有的方法论/框架打包成 skill：
```
skills/industry_analysis/     # 产业分析（生命周期/波特五力/利润池）
skills/decision_memo/         # 决策备忘录写作（FP0/作者姿态/框架清单）
skills/roundtable_review/     # 圆桌评审（多角色批判 prompt）
```
**收益**：写报告自动加载对应 skill，框架不再靠记性；圆桌评审一键触发。

### 二期：Subagent 并行（中期，1周）
```
研究型：写报告前并行派调研 agent
  → research_competitor / research_policy / research_supply_chain
评审型：写完后派独立评审 agent
  → reviewer_ib（投行视角）/ reviewer_mbb / reviewer_audit
```
**收益**：油位 v4.6 漏波特五力的错误不会再现（skill 强制加载）；Marvis 三轮圆桌发现的问题在提交前就被 Subagent 发现。

### 三期：编排融合（长期）
```
task_router 升级：按任务类型自动组合
  批量标准 → Python 管线
  深度研究 → Python + Subagent 并行调研
  决策备忘录 → Python + Skill + 写作 + Subagent 评审
```

## 五、收益 vs 风险

### 收益
| 维度 | 现状 | 升级后 |
|------|------|--------|
| 质量 | 单 Agent 写，14版迭代 | Skill 强制框架 + Subagent 独立评审，3-4 版收敛 |
| 速度 | 串行调研 | Subagent 并行，调研 3-5 倍速 |
| 一致性 | 靠记性 | Skill 标准化 |
| 可信 | Python 门禁 | Python 门禁 + Subagent 评审双保险 |

### 风险与缓解
| 风险 | 缓解 |
|------|------|
| Subagent 引入新 AI 痕迹 | Subagent 也加载"作者姿态"skill + 门禁扫描 |
| Skill 膨胀难维护 | 按领域分组，复盘时沉淀（油位迭代教训） |
| 过度工程 | 一期只做 Skill 化（低成本），二期按需上 Subagent |
| 上下文超限 | 2hao-context-guard + 磁盘 checkpoint（已有） |

## 六、集思广益——结合实战的判断

**如果按此架构，油位报告会怎么走？**
- v2.3 用 Python 管线生成骨架（数据/财务）
- 写前加载 industry_analysis + decision_memo skill → 框架自动覆盖（不会漏波特五力）
- 写作用"作者姿态"skill → 不会引入元评论语言
- 写完派 reviewer_ib/mbb/audit 三个 Subagent 并行评审 → Marvis 三轮圆桌的 Critical 在提交前就被发现
- 14 版迭代 → 预计 4-5 版收敛

**一句话**：Python 是地基（确定性）、Subagent 是手脚（并行深度）、Skill 是大脑（方法论）——三者不是替代，是各司其职的完整架构。**值得升级，且应分层渐进：先 Skill 化（成本最低），再 Subagent 并行（收益最大）。**

---

## 七、我的最终建议

```
✅ 升级，但分层：
  1. 现在做：Skill 化（industry_analysis / decision_memo / roundtable_review）
     → 解决"框架靠记性"和"圆桌手动触发"
  2. 短期做：Subagent 并行（研究型 + 评审型）
     → 解决"单 Agent 质量天花板"和"串行调研慢"
  3. Python 保留：确定性计算/门禁/导出（0 token，已证明）

❌ 不做：推翻 Python 管线重构——那是把已验证的地基拆了重盖
```

**理由**：油位 14 版迭代证明——质量瓶颈不在 Python 引擎（门禁全绿），在"单 Agent 写作缺外部批判"和"框架靠记性"。Skill + Subagent 正好补这两个短板，且不破坏已验证的 Python 地基。
