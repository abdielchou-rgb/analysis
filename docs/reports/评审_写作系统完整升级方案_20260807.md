## 一、对方案的理解（确认理解到位）

### 1.1 改造目标

三件事，一个杠杆：**更快、更好、更省 token**。核心判断是"省 token 的杠杆在架构层（路由/缓存/过滤，90% 量级），不在提示词层（10%）"——我认同。

### 1.2 架构逻辑

```
三通道各司其职：
  DeepSeek   P0 主力   → 扛实时关键链（并发 3-5），L1 chat / L2 reasoner
  OpenRouter P1 兜底   → 降级 + 终局圆桌异源评审
  Marvis     P2 免费   → 只在后台异步预取草稿（短超时回退）

叠加三层能力分级：
  L0 能 Python 的 Python（0 token）
  L1 简单语义任务 chat
  L2 深度写作/终审 reasoner

配套质量护栏：
  模块级重算替代全量重写 + Fail-fast verifier 前置 + 终局圆桌
```

### 1.3 主要工程方案（三大支柱）

| 支柱 | 内容 | 治什么 |
|------|------|--------|
| A 执行模式升级 | agent_provider priority -1→10、LLM_PROVIDER=deepseek、超时 300s→60-90s、并发上限 3-5 | 慢（60% 队列空等 + 30% 串行重写） |
| B 成本架构升级 | 三通道路由、L0/L1/L2 分级、context caching、Marvis 免费预取、批处理合并 | 贵（token 成本） |
| C 质量架构升级 | 模块级重算、Fail-fast verifier、终局圆桌、来源标记+成本日志 | 倒退（R79-R87 振荡） |

分阶段：P0 立即做（零成本）→ P1 短期做（中成本）→ P2 中期做（高成本）→ P3 可选（沙箱迁移）。

**一句话总结方案**：把"单通道固定执行"改为"三通道按需路由"，把"全量重写"改为"模块级重算"，把"人肉等 300s"改为"并发 + 快速失败"。

## 二、方案诊断与代码现状核对（关键：哪些是真的，哪些已被修复）

我逐条核对了方案根因诊断与实际代码，**发现方案有两处诊断需要修正、一处根因是真实 bug、一处方向正确但描述过时**。

### 2.1 ✅ 真实 bug：agent_provider priority 语义反转（方案 P0 修对了）

`core/deepseek_client.py` 的 `ProviderRegistry.get_best()` 与 `call_llm._active()` 均按 `priority` **升序**排序取第一个 —— **数字越小优先级越高**（`ProviderConfig` 注释亦写明"越小优先级越高"）。

而 `core/agent_provider.py`：

```python
def __init__(self, name="agent_provider", priority: int = -1):
    ...
    # R81（2026-08-06）：设为 -1，低于 DeepSeek(0)/Ollama(0)，
    # agent_provider 仅兜底
```

**注释意图（R81：做成兜底）与实际行为（-1 = 最高优先级）恰好相反。** 在 `provider="auto"` 或 DeepSeek 故障后的全量回退轮（R77 逻辑），agent_provider 会被**最先**尝试。`deepseek_client.py` 底部"import 即触发自动注册（priority=99）"的注释同样是过时残留（实际注册的是 -1）。

→ **方案 P0 的 `-1 → 10` 修正是正确的**，而且这是整个方案里唯一一处"代码 bug"级别的真问题。但要修根治，建议把 priority 改为显式枚举常量（`PRIMARY=0 / FALLBACK=50 / LAST=100`），防止同类"注释意图与实际相反"再演。

### 2.2 ⚠️ 需修正："300s 空等"占比 60% 的估计过时了

方案把"agent_provider 队列模式 300s 上限"列为慢速根因 #1（~60%）。但代码显示已有两层缓解（方案未提及）：

1. **R77 心跳快速失败**（2026-08-05）：`agent_provider.py` 检查 `.heartbeat` 文件，30s 内无心跳 → **立即抛错回退 DeepSeek**，不再空等 300s；
2. **R53 健康预检**（2026-08-03）：`call_llm` 对 HTTP provider 先 5s 探活，连接层失败直接跳过，避免"6 组并行各等满 300s、一轮空耗 10 分钟"。

**因此"300s 空等"只在 responder 存活但响应慢、或质量重等（R67 护栏删坏响应重等）时发生。** 60% 的占比估计偏高，P0 若按此验收可能修掉已经修过的东西。

→ 建议：P0 先跑基线计时（复用 `logs/`、`report_cache`、`observability.db` 已有记录），确认当前慢在哪，再定验收数字，别拍 2-5x。

### 2.3 ⚠️ 需修正："全量重写"占比 30% 的描述过时

方案引用 R79-R87 八轮全量重写不收敛（0.856→0.827 振荡）作为"全量重写"根因。方向正确，但代码里已有局部重写机制：

- `pipeline/write_revise_loop.py` + `write_checkpoint.py`（checkpoint 断点恢复）
- `pipeline/fail_segment_locator.py`（R53 P0-2：组级局部重写，只重跑失败组）
- R66 修复：图表失败短路 → 全量重写 → **段级局部重写**

→ 方案 P2 的"模块级重算"应标注为**强化已有**（版本管理 + 影响范围传播目前缺），而不是从零新建，否则重复造轮子。

### 2.4 🔴 方案未处理：宪法级冲突

`CLAUDE.md` 明文：**"LLM 只走 DeepSeek（.env 仅 DEEPSEEK_API_KEY）"**、单 Provider + L3 Agent 兜底。方案要引入 OpenRouter 三通道 = 修改宪法级决策，**必须用户明确拍板**，且落地时要同步修订 CLAUDE.md 的"LLM 策略"章节（R83 教训：决策必须回流，不能文档与代码脱节）。

### 2.5 ✅ 方案方向正确、应予确认的部分

- **"换宿主无意义"**：瓶颈在执行模式不在宿主框架 —— 对，OpenClaw/Hermes 迁移救不了队列空等；
- **L0/L1/L2 分级**：与现有 R13 三算力架构（deepseek / ollama_local / agent_provider）天然吻合，是"架构层省 token"的正解；
- **模块冻结不重写**：与 R79-R87 教训一致；
- **一次授权协议 + 工作区隔离**：落地成本低、收益直观，是内容污染组合拳的正确起点。

## 三、优化建议（按优先级排列）

### P0 前置（动手前先做）

1. **先测后改，再定验收**：P0 验收"单篇耗时降 2-5x"目前不可验证。先跑一篇现状基线（计时落盘），确认慢点分布，再定 target。否则可能把预算花在已修复的环节上。
2. **priority 语义根治**：`-1 → 10` 是补丁，建议同时把 priority 改成显式枚举 + 单元测试锁定排序语义（`test：agent_provider 必须排在 deepseek 之后`），防止 R81 这类"注释意图与实际相反"再发生。
3. **R67 质量重等机制改造**：当前"坏响应删除重等（窗口内）"是隐性时间黑洞。改为**坏响应立即返回给调用方，并标记 `fallback_source=agent_poor_quality`**，让上游知道这是降级，而不是静默多等一轮。

### P1 方案增强

4. **Prompt Caching 口径修正**：方案引用的"成本 -90%、延迟 -85%"是 Anthropic 口径。DeepSeek 的 context caching 是**自动磁盘缓存**，计费与折扣口径不同，**不能直接套用**。落地前先在真实长文档上实测缓存命中与成本，再决定是否值得做缓存前缀。
5. **圆桌异源至少一席付费**：OpenRouter 免费档模型质量波动大，把终局评审押在免费模型上风险高。终局圆桌应至少 1 席付费模型（如 OpenRouter 付费档或 DeepSeek reasoner），否则"异源评审"可能集体放水。
6. **Marvis 免费预取必须"失败即弃"**：历史实证"5 章并行全挂仅留首章"。预取语义必须是：结果可选、失败不阻塞主链、过期自动丢弃、**绝不进入终稿合并层**（只作候选草稿，过 verifier 才能用）。否则预取会成为新的 300s 风险点。

### P2 结构性

7. **模块级重算 = 强化已有，不是新建**：复用 `write_checkpoint.py` + `fail_segment_locator.py` + `write_revise_loop.py`，只补"模块版本管理 + 影响范围传播"两块。
8. **成本日志复用 observability.db**：`core/observability.db`、`edit_history.py`、trace 日志已记录节点级信息，方案不必另起炉灶，扩展 schema + 加一层"每节点 token/模型/耗时"即可。
9. **宪法同步写入实施计划**：三通道落地时必须同步修订 `CLAUDE.md`（LLM 策略章节）与 `docs/CLAUDE-architecture.md`，否则文档与代码脱节（R53/R83 教训）。

### 暂缓 / 商榷

10. **P3 沙箱迁移**与用户"本地优先"工作流画像冲突。沙箱只跑编排层、数据获取留本机，收益是隔离但成本高、引入新的环境适配面。建议明确缓行，除非有具体的"必须隔离"用例。

## 五、结论

**方案整体成立，值得执行。** 三大支柱方向正确，根因分析的大部分逻辑站得住，尤其是"换宿主无意义"、"架构层省 token"、"模块冻结不重写"三个判断我完全认同。

但在动手前需要做三件事：

1. **修正两处过时诊断**：300s 空等已被 R77/R53 缓解、"全量重写"已有局部重写实现 —— P0 之前先跑基线，把钱花在真正慢的地方；
2. **确认一处宪法级决策**：三通道 = 修改 CLAUDE.md 单 Provider 红线，需要用户拍板并同步改文档；
3. **落地一处真实 bug 修复**：agent_provider priority -1 语义反转，是方案里最有价值的"真 bug"，P0 必修。

**优先级建议**：P0（修 priority + 基线 + 超时下调）→ P1（三通道 + L0/L1/L2 + Marvis 预取带失败即弃）→ P2（强化模块级重算 + 成本日志）。P3 沙箱暂缓。

## 六、主文档增量评审（写作OS / 内容污染 / 授权协议 / 弹性设计）

> 补充评审对象：`写作系统全案_对话调研思考改造方案_20260807.md`。该文档比汇总文档多出五块内容：写作OS五层架构、内容污染组合拳、一次性授权协议、模块弹性设计（ADaPT）、TQC投机执行。逐一核对与 2hao 现况的关系。

### 6.1 写作OS五层架构 —— 范式升级，但必须渐进

| 层 | 方案设计 | 2hao 现况对照 | 判断 |
|----|---------|--------------|------|
| ① 技能库层 | 沉淀标准模块为可复用 Skill | 已有 `core/frameworks`、`core/methodology`、`core/knowledge` | ✅ 有雏形，缺"标准化 Skill 接口" |
| ② 组装层 | 主题→FP→大纲→按需加载→写作宪章 | `report_planner` + `analyst_planner` + SAC YAML | ✅ 已有，缺"动态组装" |
| ③ 执行层 | 叶子并行→串行合并→宏观重构 | 维度并行（DIM_PARALLEL）非叶子并行 | ⚠️ 差异最大，见 6.2 |
| ④ 连贯保障层 | 写作宪章+共享事实库+大纲冻结+证据锚点+工作区隔离 | StyleCompiler + SAC + `evidence_chain` | ✅ 大部分已有 |
| ⑤ 门禁层 | 过程 verifier + 终局圆桌 | IronGate + critic 5席 | ✅ 已有，缺"每层 verifier" |

**核心判断**：写作OS是真正的范式升级——把 2hao 从"模板机"（SAC 固定维度驱动的管线）变成"操作系统"（动态组装）。方向对，但 **2hao 的 SAC 26 维 + E2E 管线是 R1-R87 多年沉淀的已验证骨架，推翻重建风险极高**。

→ 建议：**保留 SAC 骨架，在其上叠加"弹性分解层"**（6.4），而不是让动态组装取代固定模板。两个可以共存：简单标的走 SAC 固定骨架，复杂标的在固定骨架上按需分解。

### 6.2 内容污染组合拳 —— 方向正确，需适配 2hao 的实际污染形态

方案 7 条组合拳（工作区隔离/时间隔离/选择加载/读写分区/预算管理/交叉污染检测/合并verifier）方向全部正确。但 **2hao 的污染形态与方案假设的"多写手并行"不同**，需适配：

| 方案假设 | 2hao 实际形态 | 适配动作 |
|---------|--------------|---------|
| 多 Sub-Agent 并行写共享工作区 | **单进程跑完 E2E**，无多写手 | 工作区隔离主要解决"多篇报告共享 output 目录"的文件层污染 |
| 长会话连续写多篇的上下文残留 | 单次调度一个标的，但会话可能复用它篇上下文 | **时间隔离**（新任务=新上下文）对 2hao 最有效，落地成本最低 |
| 事实库只读 | `edit_learning.db` / `findings_db` 全写，无只读分区 | 新增"证据池只读"概念，需要改造数据写入路径 |
| 后写章节继承先写章节错误 | R48 已有"标的隔离校验"防串标，但章节级继承仍可能 | 合并层 verifier 已有雏形（`evidence_chain`），强化即可 |

**最值得立刻做的**：工作区隔离（`00_input/10_draft/20_output/90_temp`）——2hao 当前所有报告产物混在 `output/` 与根目录（根目录已有 30+ 个 `gate_*.txt` 调试残留，正是污染形态），独立工作区是低成本高收益的第一层。**注意根目录卫生**：先清理 gate_*.txt / fixgate*.py / sacdump 等调试残留，再谈工作区规范。

### 6.3 一次性授权协议（Pre-flight Authorization）—— 值得做，但要 CLI 化

方案设计（启动问卷→预声明授权范围→执行中零打断→交付审计）与 2hao 高度契合：2hao 是"跑完看 Gate 报告"的模式，缺一个"起飞前问清"环节。**启动问卷锁定受众/硬决策点/风险偏好，能减少"跑完发现方向错"的整篇返工**——这正是 R79-R87 振荡的另一面。

→ 建议适配：2hao 是调度管线不是交互式 IDE，启动问卷应做成 **CLI 参数 / JSON 配置**（复用 `--enrich-file` 的 JSON 模式），不引入 GUI 交互，保持可脚本化。SAC YAML 升级为标准问卷模板可行。

### 6.4 模块弹性设计（ADaPT 按需分解）—— 有价值，但分阶段

方案三个自由度（深度×宽度×粒度）+ 按需分解信号（字数超预算/证据不足/逻辑复杂/门禁失败）方向正确，与 TQC 的 L0/L1/L2 分级呼应。

与 2hao 对接的落地顺序（由易到难）：

1. **弹性预算（最容易）**：每个 SAC 维度/章节带 token/字数预算，触及上限未完成 → 标记"需分解"，报告尾部诚实留白（R79 已有"诚实留白"基础）。这是纯计算层改动，可验证。
2. **异构路由（次之）**：检索类节点（窄而浅，低深度高并行）vs 推理类节点（深而少）vs 写作类节点——与三通道的 L0/L1/L2 映射，P1 可做。
3. **按需分解（最难）**：compute_engine 支持动态子模块，需要 compute 层重构。建议 P2 起步。

### 6.5 TQC 投机执行 —— 对 2hao 高风险，必须限定边界

方案 TQC ④ 引用 AWS speculative execution：用预测的上游输出提前启动下游。**对 2hao 风险高**——管线大量节点有副作用（写 SQLite、写盘、写 edit_learning.db），猜错回滚在"有副作用的节点"上会产生脏数据（R48 串标事故就是写共享库的教训）。

→ 建议：投机执行**仅限纯计算节点**（如图表布局预生成、格式校验预跑），**不可逆/有副作用的节点一律不做**。并且方案自己也标注了安全前置（side-effect-free/idempotent/commit barrier），这条红线要写进实施计划。

### 6.6 UltraThink 10 步流程 —— 不必照搬，映射到现有节点即可

| 10步 | 2hao 对应 | 缺口 |
|------|----------|------|
| 1 FP 拆解 | `report_planner` / `analyst_planner` | ✅ 已有 |
| 2 调研并行 | `data_collector` + data_feeds | ✅ 已有 |
| 3 头脑风暴 | 部分（SAC 维度无 STORM 式多视角） | 可选增强 |
| 4 主 Agent 定稿大纲 | `report_blueprint` + SAC | ✅ 已有 |

## 七、主文档增量评审结论

主文档比汇总文档更完整地勾勒了"写作 OS"愿景，但**核心可落地价值集中在三处**：

1. **内容污染组合拳中的工作区隔离**（+根目录卫生清理）——最低成本最高收益，建议作为 P0.5 先行；
2. **一次性授权协议 CLI 化**（启动问卷 JSON 化）——减少方向性返工，P1 可做；
3. **弹性预算**（SAC 维度 token/字数预算 + 诚实留白）——纯计算层改动，P1 可做。

**明确不做/暂缓**：TQC 投机执行（副作用节点高风险，仅限纯计算节点）、临时 Skill 动态生成（2hao 不需要）、写作 OS 推翻 SAC 骨架（渐进叠加弹性层，不重建）。

**与汇总方案合并后的总优先级**：

```
P0.5  工作区隔离 + 根目录卫生清理（成本≈0，收益立现）
P0    修 agent_provider priority 语义反转（真 bug）+ 跑基线
P1    三通道 + L0/L1/L2 分级 + 启动问卷 CLI 化 + 弹性预算 + Marvis 预取"失败即弃"
P2    强化模块级重算（版本管理+影响传播）+ 证据链增强 + 按需分解（compute 层）+ 成本日志
暂缓  TQC 投机执行（限纯计算节点）、沙箱迁移、临时 Skill、写作 OS 重建
```
