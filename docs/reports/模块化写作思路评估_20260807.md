# 模块化写作：切N模块→并行→组装→局部修——思路评估与顶级理解

> 日期：2026-08-07
> 对象：2hao-analyst 写作管线升级方向
> 结论先行：**思路方向完全正确，是当前长文生成的主流范式（AgentWrite/STORM/CogGen/各工程实践一致指向它）。但"组装"和"局部修复"是两个最大的坑——方案对组装难度的估计不足，对"只改小模块"的适用边界没划清。**

---

## 一、核心思路：成立吗？

一句话：**成立，但不是免费的。** 这套思路的本质是"用上下文工程换 token 和延迟"——把一个大 prompt 的写作任务拆成 N 个小 prompt，换取：

| 收益 | 机制 | 代价 |
|------|------|------|
| 快 | 叶子模块可并行（无依赖） | 组装串行（必须有依赖顺序） |
| 省 | 每模块只带自己的事实切片（不整库灌入） | 跨模块引用需要额外机制 |
| 稳 | 短任务幻觉低（arXiv 2505.00127：错误回答显著更长） | 拼接处连贯性差（AgentWrite 实证） |
| 可修 | 模块独立版本，坏哪改哪 | **必须能精确定位坏模块，否则"只改小模块"失效** |

四个收益全是真的，但每个都对应一个代价。**方案的成败取决于：组装质量 + 故障定位精度**。这两点恰好是 2hao 目前最薄弱的环节（R79-R87 振荡、R53 P0-2 死代码都出在这里）。

---

## 二、顶级理解（按"切分→并行→组装→修复"四个环节组织）

### 2.1 怎么切（Decomposition）

| 方法 | 来源 | 核心机制 | 对 2hao 的启示 |
|------|------|---------|---------------|
| **大纲先行（Outlining）** | AgentWrite（LongWriter, arXiv 2408.07055） | 先规划（子主题→子要点+写作约束），再逐段并行写，最后拼装 | 大纲 = 模块边界，是切分的唯一依据；**大纲必须冻结**，写作中不漂移 |
| **按需分解（As-Needed）** | ADaPT（AllenAI） | 先粗后细：先尝试执行子任务，执行不了/超载才递归下拆 | 不要预铺满 N 个模块；先按粗粒度切，触发信号（超预算/证据不足/门禁失败）再拆 |
| **认知任务分类** | Beyond Outlining（arXiv 2503.08275） | 检索/推理/写作三类任务，弹性参数不同 | 检索模块窄而浅（高并行），推理模块深而少（低并行），别一刀切 |
| **动态树构建** | DTCRS（ACL 2025） | 按需动态建树替代固定层级 | 模块树结构可中途调整（合并薄节点/拆分厚节点） |

**切分的粒度共识**：论点单元 **200-500 字**最稳（比"一段"大、比"一节"小），兼顾论证完整与幻觉抑制。大于 1000 字触发分解，小于 100 字与邻节点合并（双向弹性）。

### 2.2 怎么并行（Parallelism）

- **叶子并行 + 合并串行**（AgentWrite 实证）：并行只到叶子模块；**合并必须串行**。并行写出来的整篇连贯性远差于串行——这是硬证据，不是观点。
- **无依赖叶子才并行**：同一层无数据依赖的模块才可同时写；有依赖的（如"行业→竞争→估值"）必须等上游。
- **并行数上限**：Anthropic 实测多智能体 token 消耗 ≈ 单聊 15 倍。**并行省的是墙钟时间，不省 token**——甚至更费。规模分级（简单 8-12 模块，复杂才 40+）是防过度工程的硬约束。

### 2.3 怎么组装（Assembly）——**方案最大的坑**

| 挑战 | 证据 | 解法 |
|------|------|------|
| **合并放大幻觉** | Context-Aware Hierarchical Merging（ACL 2025 Findings） | 合并时不能只传子模块摘要，**必须带源上下文**（摘要+关键证据+可回溯指针） |
| **拼接处断裂** | AgentWrite / 多 agent 写作工程实践 | 组装不是简单拼接；需要过渡段生成器（衔接句）+ 大纲校验（各段是否覆盖全部要点） |
| **一致性** | 长篇创作工程（分层记忆/写作宪章） | 共享术语表+数字口径+风格指纹（**写作宪章**），写手任务自带，而不是事后统一 |
| **顺序敏感** | 多 agent 共享状态（ghost context） | 组装顺序固定（自底向上 5-8 一组），结果不随执行顺序漂移 |

**关键反直觉点**：很多人以为组装只是"拼起来"，但证据一致指向——**组装层是质量流失最严重的地方**。2hao 的 `_editor_merge` / assemble 步骤正是这一环，Marvis 方案对它的笔墨远少于对并行/路由的笔墨，**预算分配不合理**。

### 2.4 怎么修复（Local Repair）——**"只改小模块"的适用边界**

| 修复粒度 | 适用场景 | 证据/依据 |
|---------|---------|----------|
| 小错→**精炼**（Self-Refine） | 局部瑕疵/措辞/单点数据 | 生成→批判→精炼；直接丢弃浪费正确部分 |
| 大错→**重建**（丢弃重写） | 方向性错误/核心事实错误/逻辑断裂 | 批判反馈必须"定位问题+给修复方向" |
| 深度不够→**补子模块**（elaborate） | 方向对但单薄 | 保留骨架，拆 1-2 子论点，父模块只重写过渡段 |
| 崩溃→**checkpoint 回滚** | 任意点中断 | 从最近 checkpoint 恢复，只重跑失败段 |

**三个必须知道的真相**：

1. **"只改小模块"的前提是定位准确**。改错模块 = 改完好模块 + 坏模块原样留存 = 白花 token。定位器（fail_locator）误伤率必须低（R79 教训：归因正则过宽误伤）。
2. **局部修复需要依赖图**。改 A 模块，B/C 引用 A 的事实/结论 → B/C 必须"待重校验"。没有影响范围传播，局部修复会引入新的不一致（这正是 R84-R85 一直追的"数据锚定"问题）。
3. **版本管理是修复的地基**。模块要有 v1/v2/v3，保留历史可回滚，否则"只改小模块"无法落地（怎么知道改了没改、回退到哪）。

### 2.5 工程级对照（非论文，真实踩坑）

| 实践 | 关键机制 | 一句话 |
|------|---------|--------|
| 25 agents 写 60 页书 | 大纲冻结 + 章节并行 + 主 agent 一致性把关 | 真实证明可行，但作者强调"主控一致性是灵魂" |
| OmniWriter | LangGraph 并行写作 + RAG 幻觉抑制 + 上下文管理 | 组装与上下文管理是基础设施，不是可选项 |
| Plan→Commit | LLM 只出提案，确定性校验后提交 | **LLM 输出当"提案"不当"成品"，过校验才提交——对 2hao 的 Gate 是直接映射** |
| 长篇创作分层记忆 | 大纲级/章节级/段落级分层存储 | 一致性靠分层记忆 + 迭代工作流，不是靠单次生成 |

## 三、对 2hao 的直接建议（落地口径）

### 3.1 这条思路与 2hao 现况的差距

| 模块化写作要求 | 2hao 现状 | 差距 |
|--------------|----------|------|
| 大纲冻结 + 证据锚点 | report_blueprint + SAC | ✅ 基本有 |
| 叶子并行 | **维度并行**（DIM_PARALLEL，3 段并行） | ⚠️ 粒度太粗（段级不是论点单元级） |
| 组装带源上下文 | `_editor_merge`（3 段合并） | ⚠️ 合并只传摘要，无证据链（ACL 2025 反例） |
| 局部修复 | write_revise_loop + fail_segment_locator | ⚠️ 有雏形，但定位器归因精度不足 |
| 版本管理 + 影响传播 | 无 | ❌ 完全缺失（最大缺口） |
| 写作宪章 | StyleCompiler + SAC + 模板黑名单 | ✅ 有 |

**结论**：2hao 距"模块化写作"只差三块——**更细的切分、带证据链的组装、版本管理+影响传播**。前两块是强化，第三块是从零。

### 3.2 建议实施顺序

```
P1  把维度并行改为"论点单元级"并行（200-500字），复用现有 dimension_grouper 拆层
P2  组装升级：_editor_merge 传"摘要+证据引用+指针"（改 ACL 2025 反例为正面），合并时过证据链 verifier
P3  模块版本管理 + 影响范围传播（引用关系图：模块→依赖其的模块列表），Gate 改模块级
P4  定位器精度提升（fail_locator 归因到段落级，复用 R83 的问题覆盖率经验）
```

### 3.3 红线（必须守住）

1. **合并串行，绝不并行**（AgentWrite 硬证据）；
2. **组装必须带源上下文**，不能只传摘要（ACL 2025 反例）；
3. **只改小模块的前提 = 定位准确 + 影响传播**，两条缺一不可，否则退回全量重写；
4. **并行省时间不省 token**，规模分级是硬约束，别被"更快更省"双承诺误导。

---

## 四、一句话总结

你的思路是对的——**它就是当前长文生成的主流范式（论文与工程实践一致指向）**。但三个坑要正视：**组装是质量流失最严重的地方**（预算分配要对齐），**"只改小模块"依赖定位精度与影响传播**（2hao 目前缺版本管理这一最大缺口），**并行省时间不省 token**（规模分级别省）。方向不用怀疑，把力气花在组装层和修复地基上。
