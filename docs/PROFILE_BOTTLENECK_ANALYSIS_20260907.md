## 三、真实瓶颈定位（证据 + 代码锚点）

### 1. research_planner：注释说谎 + 每维串行 LLM（P0 修正）

- `pipeline/e2e_orchestrator.py:478` 注释写 **"P3-B: research_planner v1——确定性研究规划（零 LLM）"**；
- 实际 `pipeline/research_planner.py:133-168`：`use_llm=True` 时**每维度独立调 `call_deepseek`**（`_llm_generate_questions`，L112-118），6 路 `ThreadPoolExecutor` 并行；
- 结果：7 次采样中位 155s、均值 388s、一次 **1219s（20 分钟）**。
- 它是 e2e 主链节点（deps=["enrich"]），**每份报告都跑**，且是超时重试重灾区（deepseek 180-300s 超时 → 每维重试 → 6 维 × 重试 = 十几分钟）。
- **修正方向**：① 注释纠偏（零 LLM→LLM 增强+模板回退）；② 每维调用加**总预算/熔断**（不是每维独立无限重试）；③ 6 路并行改**有界并发 + 超时共享**；④ 确认是否需要全维度 LLM——多数维度模板已够，LLM 只留给冲突/追问维度。

### 2. write_sections：真第一稳定大头（P0 优化目标）

- 38 次采样中位 107s、均值 270s、**max 2502s**；
- 这是多段并行写 + merge 的整节点耗时。中位 107s 意味着"并行写 N 段"实际被**最慢段 + 串行 merge** 拉长；
- 修正方向：profile 到**段级**（哪一段最慢、是否某段反复自愈重试）；对慢段单独降级模型或降档（本地草稿→deepseek 精修）；不是加 data-hash 缓存。

### 3. 重尾极值：比中位数更该治（P1）

- data max 783s / record_results max 765s / validate p90 96s max 370s / preflight max 121s——**偶发灾难性慢调用**把单轮从 ~6 分钟拖到 20-40 分钟；
- 修正方向：**全局单次调用预算 + 熔断**（已有 circuit-break 是"失败项"维度，缺"耗时"维度）；超时从"每节点独立"改成"共享总预算"；对超长调用降级（用缓存/本地兜底）。

## 五、一句话结论
