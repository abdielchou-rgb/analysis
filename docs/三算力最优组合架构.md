# 2hao 报告生成：三套算力最优组合架构

> 目标：在**保证 2hao 报告质量**（SAC 全覆盖 + IronGate 通过 + 数据零编造）的前提下，把报告生成效率提到最高。
> 资源：DeepSeek（云端 API）、本地大模型（Ollama）、Marvis（agent 值守队列）。
> 原则：**不考虑 token 成本，只求质量 × 速度最优。**
> 日期：2026-08-01

---

## 一、现状事实：三套资源的能力画像

| 资源 | 能力 | 单次响应 | 质量 | 关键约束 |
|---|---|---|---|---|
| **DeepSeek** | 云端 API，最强推理 | 60-120s（8192 token） | ★★★★★ | 串行是瓶颈，所有调用排队 |
| **本地 Ollama** | 本地推理，已自动检测 | 5-30s | ★★★☆ | 机械任务足够，创作略弱 |
| **Marvis** | agent 值守队列，可并行多实例 | 60-120s/请求 | ★★★★ | 慢但可**多实例并行**，能做研究/结构化 |

### 管线耗时瓶颈（实测）
- 每份报告 **12-16 次 LLM 调用**，95% 时间花在 LLM 上
- 当前并行：write 3 段并行 + critic 5 席并行
- **根本瓶颈：所有高价值调用都串行排队等 DeepSeek**（Bold Call 辩论 3 连、Gate LLM 检查、revise 循环）
- 最慢路径：写 3 段(~2min) → 辩论 3 连(~3min) → Gate 检查(~2min) → critic 5 席(~2min) → 可能 revise 重写(~2min/轮)

### 核心洞察
**DeepSeek 是稀缺资源。** 提速的本质不是"让 DeepSeek 更快"，而是**把机械任务下沉到本地、把可并行任务甩给 Marvis，让 DeepSeek 只做最高价值的创作**。同时用**资源级流水线并行**——Marvis 起草的同时 DeepSeek 做辩论，而不是全部排队。

## 二、最优架构：三资源分层 + 流水线并行

### 2.1 总览

```
┌─────────────────────────────────────────────────────────┐
│                数据层（确定性代码，零 LLM）              │
│  data_collect → enrich → compute → charts               │
│  （本就不慢，保留；compute 已下沉确定性计算，见 4.4）    │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│            写 作 层（骨架先行 + 分段深化）              │
│                                                         │
│  Step1 骨架并行（Marvis ×3）                             │
│  ├ seg1 战略层 骨架 ← Marvis A                         │
│  ├ seg2 竞争层 骨架 ← Marvis B                         │
│  └ seg3 前瞻层 骨架 ← Marvis C                         │
│          ↓ 骨架合并（DeepSeek 1 次调用，治乱序）        │
│  Step2 分段深化（Marvis ×3 并行，逐段扩写）             │
│          ↓ 各段就绪                                     │
│  Step3 资深编辑合并（DeepSeek 1-2 次）                  │
│  └ 修一致性 / 强 Bold Call / 补 SAC 缺口                │
│  全程并行：DeepSeek 同时做 Bold Call 辩论（不排队）     │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│              校 验 层（本地模型承接机械检查）            │
│                                                         │
│  本地 Ollama：score_text / ai_tone / 格式检查 / critic   │
│  席位 4-5（低价值高量，本地 5-30s 秒级）                 │
│  DeepSeek：critic 席位 1-3（高价值评审，保质量）         │
│  IronGate 全量（质量兜底，不降级）                       │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│             修 订 层（局部修订 + 多资源并行候选）        │
│                                                         │
│  Gate 失败 → 只修失败段（R7 状态锚点定位）               │
│  不推倒重写                                             │
└─────────────────────────────────────────────────────────┘
```

### 2.2 写作层采用「骨架先行 + 分段深化」（AgentCPM 范式）

**为什么**：一次让 LLM 写长段落（8192 token）既慢又容易结构松散（我们圆桌发现的段落乱序/重复根因）。AgentCPM-Report 的「交替起草与深化」范式证明：**先并行起草各段骨架 → 合并定序 → 再并行深化扩写**，单次调用 token 少、延迟低、结构更稳。

**三资源下的落地**：
1. **Step1 骨架并行**：Marvis ×3 各起草一段骨架（标题 + 要点 + 数据引用占位，~1500 token/段，秒级）
2. **骨架合并**：DeepSeek 1 次调用，把 3 段骨架合并成统一结构（治乱序/重复），产出最终章节骨架
3. **Step2 分段深化**：Marvis ×3 按合并后的骨架并行扩写（~4000 token/段）
4. **Step3 资深编辑合并**：DeepSeek 读 3 份深化稿 + 数据字典，合并润色（修一致性、强 Bold Call、补 SAC 缺口）

**对比直接起草**：骨架先行多 1 次调用，但每段深化有明确骨架约束 → 结构质量显著提升，且 Marvis 深化阶段可以更快（不用边想结构边写）。

## 三、每个节点的资源分配（具体到调用）

| 节点 | 当前 | 优化后 | 理由 |
|---|---|---|---|
| data_collect/enrich/compute | 确定性代码 | 不变 | 零 LLM，已最优 |
| **seg1 战略层** | DeepSeek | **Marvis A** | 起草类任务，SAC 模板保证结构 |
| **seg2 竞争层** | DeepSeek | **Marvis B** | 同上，并行 |
| **seg3 前瞻层** | DeepSeek | **Marvis C** | 同上，并行 |
| **Bold Call 辩论**（3连） | DeepSeek 串行 | **DeepSeek 并行于起草** | 高价值，DeepSeek 独占，不排队 |
| **合并 + 润色** | 无（直接拼） | **DeepSeek 1-2 次调用** | 资深编辑：修一致性/强 Bold Call/补 SAC 缺口 |
| **score_text**（Gate） | DeepSeek | **本地 Ollama** | 机械评分，本地秒级 |
| **ai_tone 检查** | DeepSeek | **本地 Ollama** | 正则+分类，本地够 |
| **critic 席位 1-3** | DeepSeek | DeepSeek | 高价值评审，保质量 |
| **critic 席位 4-5** | DeepSeek | **本地 Ollama** | 冗余席位，本地够 |
| **revise 失败段** | 全重写 | **只修失败段** | 局部修订，Marvis/DeepSeek 按需 |
| IronGate 全量 | 硬校验 | 不变 | 质量兜底，**永不降级** |

### 关键设计：资源级流水线并行

```
t=0min   Marvis A/B/C 并行起草 3 段 ────────────────┐
         DeepSeek 并行做 Bold Call 辩论 ──────────┐ │
t=2min   草稿齐 + 辩论齐                          │ │
         DeepSeek「资深编辑」合并润色（1-2 调用）  ←┘ │
t=4min   报告初稿 → 本地评分 → critic 并行        ←──┘
t=5min   IronGate 校验 → 达标交付
```

**对比现状**：现状 DeepSeek 串行做「写 3 段 → 辩论 → Gate → critic」，约 9-10 分钟初稿，revise 后 20-30 分钟。
**优化后**：Marvis 起草与 DeepSeek 辩论**并行**，初稿约 4-5 分钟，revise 局部修，**总时间 5-10 分钟**，**提速 2-4 倍**。

## 四、为什么质量不降（质量保障机制）

| 质量风险 | 保障机制 |
|---|---|
| Marvis 草稿质量低于 DeepSeek？ | **DeepSeek 资深编辑合并**——不是直接拼草稿，而是 DeepSeek 读 3 份草稿 + 数据字典，修一致性、强 Bold Call、补 SAC 缺口。最终文本质量由 DeepSeek 把关 |
| SAC 维度覆盖？ | Marvis 起草用**同一套 SAC 模板 + 维度定义**（`_build_prompt_v4`），结构强约束 |
| 数据零编造（FP2）？ | 草稿/编辑都注入**共享数据字典**，数值引用 `{ref:key}`，IronGate data_dict_refs 校验 |
| 局部修订会丢一致性？ | **R7 状态锚点**（上一轮全文 + 覆盖矩阵）进 prompt，只改失败段，保留已达标段 |
| 本地模型误判？ | 本地**只做机械评分/格式检查**（score_text/ai_tone），不做创作判断。critic 高价值席位仍 DeepSeek |
| IronGate 质量兜底？ | 全量检查**永不降级**，score 不达标不交付 |

**一句话**：草稿可以来自任何资源（Marvis/本地），但**最终文本和评审必须经过 DeepSeek 质量闸**——这就是"保证质量"的底线。

## 六、与网上顶级打法的融合对照

本架构不是孤立设计，融合了前面调研的全部打法。逐一对照：

### 6.1 骨架先行 + 分段深化（AgentCPM-Report 范式）✅ 已融合
架构 2.2 节完整采用：先并行起草骨架 → 合并定序 → 再并行深化。治乱序 + 提速双赢。

### 6.2 prompt caching（DeepSeek 前缀缓存）✅ 已融合
三资源下 DeepSeek 的自动前缀缓存照样生效。**做法**：把公共前缀固定——system prompt + SAC 维度定义 + 数据字典放最前面，保证跨段共享缓存命中。
- 受益点：Marvis 深化稿被 DeepSeek 编辑时，数据字典/SAC 前缀命中 → 编辑调用降 30-50% 延迟
- **实施**：`_build_prompt_v4` 里公共部分（SAC/数据字典/方法论）固定顺序，不随段变化

### 6.3 计算任务下沉（MLAT：确定性计算当工具）✅ 已融合
- compute 节点已是确定性代码（DCF/可比/比率计算不走 LLM）
- **扩展**：更多机械任务下沉——财务比率、行业统计、估值换算，全部走代码不进 LLM
- 数据层零 LLM 已经是这个思路的极致

### 6.4 模型路由（sub-agent 分模型）✅ 已融合
三资源分层本质就是任务级模型路由：创作→DeepSeek，起草→Marvis，评分→本地。这是 Claude Code per-agent model routing 思路的 2hao 化。

### 6.5 局部修订（不推倒重写）✅ 已融合
R7 状态锚点定位失败维度 → 只重写失败段。前面方案 1 的核心。

### 6.6 推理层加速（Speculative Decoding / SPORK / LCA）⚠️ 已评估不引入
- **Speculative Decoding**：需配套 draft model，DeepSeek API 服务端支持与否不由我们控制 → 不引入
- **SPORK（自推测分叉）**：多分支共享推理进度，适合 critic 并行——但依赖推理服务端支持，API 侧不可控 → 不引入
- **LCA（KV 压缩）**：DeepSeek 服务端特性，不可控 → 不引入
- **结论**：推理层优化归"服务端可控"，我们作为 API 用户只能利用（prompt caching），不能改造。已明确交代，避免遗漏。

### 6.7 报告模板缓存（同行业复用）✅ 可选扩展
- 同行业二次报告复用已验证骨架/数据口径/Bold Call 结构 → 二次生成再降 40%
- 依赖模板质量，作为 Phase 5 可选

## 七、三资源 × 网上打法 融合矩阵

| 网上打法 | Marvis 角色 | DeepSeek 角色 | 本地角色 | 质量保障 |
|---|---|---|---|---|
| 骨架先行（AgentCPM） | 并行起草骨架 | 合并骨架定序 | — | 统一结构治乱序 |

| 模板缓存 | 复用起草 | 复用编辑 | — | 模板质量把控 |

## 八、预期收益与风险

### 预期提速
| 场景 | 现状 | 优化后 | 提速 |
|---|---|---|---|
| 首份报告初稿 | 9-10 min | 4-5 min | ~2x |
| 含 revise 完整交付 | 20-30 min | 6-12 min | **2-4x** |
| 同行业二次报告 | 复用缓存 | 模板复用 | 更多 |

### 质量保障
- **DeepSeek 永远是最终编辑和质量闸**——草稿来源多样，成品质量由最强模型把关
- IronGate 全量检查不降级——这是质量底线
- 本地只做机械任务，不做创作判断

### 风险与缓解
| 风险 | 缓解 |
|---|---|
| Marvis 草稿结构不稳 | 强 SAC 模板 + DeepSeek 编辑修正 |
| 本地评分偏差 | 先并行跑对比验证，偏差<5% 才切换 |
| 队列积压 | 3 实例并行 + 短轮询（10-20s） |
| Marvis 不可用 | 自动回退 DeepSeek 串行 |

## 九、一句话总结

**让 Marvis 当"多实例初级分析师"并行起草，让 DeepSeek 当"资深编辑"合并把关，让本地模型当"机械检验员"承接评分检查——三个资源各司其职、流水线并行。草稿可以廉价，但成品质量永远由 DeepSeek 兜底。** 这样既把 DeepSeek 从机械劳动中解放出来做高价值创作，又保证最终报告质量不降，整体提速 2-4 倍。

---

*附：本架构不牺牲质量的前提是 IronGate 全量校验作为硬闸门始终生效——这是 2hao 质量承诺的最终防线。*
