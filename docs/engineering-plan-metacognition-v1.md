## 一、核心诊断：系统的天花板在"选择层"缺失

2hao 已具备超级智能分析师的**骨架**（FP1-FP7 宪法 + SAC 维度 + IronGate 门禁 + methodology 知识库 + FP5 演化闭环），但缺**灵魂**——让智能层"选择分析路径"的机制。

当前架构把两层压扁成一层：

```
现在的系统（问题）：
  scheduler → 固定 SAC 26维 → section_writer 填空 → Gate
  LLM 只回答既定问题，不选方法、不判断框架适用性
  = 模块执行器
```

**矛盾根源**：宪法说"Agent 只管调度管线、禁止直接写报告"——这是**质量底线**（防跳过验证产生垃圾），但实现时把"底线"当成了"天花板"（禁止一切方法选择）。管线是质量地板，**不是方法天花板**。

**关键澄清**：宪法禁止的是"绕过验证直接产出"，不是"选择分析路径"。允许智能层选择方法 ≠ 允许跳过 Gate。

## 三、宪法怎么动（精准修改，不推翻）

### 3.1 顶层原则新增：FP8 — 元认知选择（Meta-cognitive Selection）

在 FP1-FP7 之后加一条，作为"智能层选择"的宪法依据：

> **FP8 — 元认知选择**
> 2号分析师不是固定流程的执行器，而是具备**方法选择能力**的分析师。面对每个分析任务，系统应：
> - **理解需求本质**：先对照 FP1-FP7 判断"这个任务考验什么维度"（数据充足度/深度/广度/时效）
> - **选择子框架**：从已吸收的方法库中选最适用的分析框架（瓶颈引擎/并购估值/深度研究/情景分析…），可组合
> - **裁剪维度**：SAC 维度按行业特征/数据可得性动态聚焦，非所有维度平均用力
> - **诚实降级**：数据不足时明确选择降级路径（估算标注/缩小范围/声明不可得），不硬凑
> - **事后反思**：报告完成后记录"用了什么框架、效果如何、下次该用什么"→ 进入 FP5 演化
>
> **边界**：元认知选择只决定"用什么方法、聚焦哪些维度"，**不豁免** IronGate 验证。任何选择路径的产出都必须通过同等门禁。选择层负责"聪明"，执行层负责"可靠"，两者不可互相替代。

### 3.2 CLAUDE.md 宪法微调（关键一改）

现状 `CLAUDE.md` 说"你只管调度，不准亲自写"——本意是防绕过验证，但字面禁止了方法选择。

**修改建议**：在"第一原则"下加一条澄清：

> **R1-补充：调度 ≠ 固定流程**
> "调度管线"不是"照抄固定步骤"。Agent 的职责包含：
> 1. **方案设计**：分析前先决定——这个标的最好用什么框架组合、SAC 哪些维度重点、哪些可精简
> 2. **方法路由**：从 methodology 知识库选择/组合子框架（瓶颈引擎/并购/深度研究等）
> 3. **灵活处理**：遇到新要求，先对照 FP1-FP8 判断归属，再决定如何融入
> 4. **边界不变**：以上选择权不豁免 IronGate 验证、不豁免数据溯源（FP2a）、不豁免反方论证（FP2b）。选择层的产物走同样的 Gate。

### 3.3 FP5 演化强化：加"方法选择学习"

FP5 现有"每次 Gate 失败被学习"，补一条：

> **【v0.1】方法选择学习**：每次报告记录 {标的特征, 数据充足度, 选用的框架, Gate分数} → 沉淀到方法选择知识库 → 下次同特征任务优先推荐高分框架组合。元认知选对方法 = 一种可学习的技能。

## 四、框架怎么写（双系统架构落地）

### 4.1 总架构：双系统

```
┌──────────────────────────────────────────────┐
│  智能层（弹性）— LLM + 元认知                   │
│  ┌────────────────────────────────────────┐  │
│  │ 分析方案规划器 (Analyst Planner)         │  │
│  │  · 理解需求 → FP映射                    │  │
│  │  · 选择/组合子框架 → 生成分析方案          │  │
│  │  · 裁剪SAC维度 → 定义重点与精简           │  │
│  │  · 诚实降级声明                         │  │
│  └───────────────┬────────────────────────┘  │
└───────────────┬──┴───────────────────────────┘
                │ 产出「分析方案」JSON（非报告正文）
┌───────────────▼──────────────────────────────┐
│  执行层（刚性）— 管线 + Gate                   │
│  · 按方案跑 data → compute → section_writer   │
│  · 子框架作为工具模块注入                     │
│  · IronGate 全量校验（不豁免）                 │
│  · 产出报告 + 方法选择记录（回喂智能层）         │
└──────────────────────────────────────────────┘
```

**核心变化**：scheduler 前加一个"方案规划"步骤，产出**分析方案 JSON**（用什么框架、重点维度、降级策略），管线按方案执行。方案不豁免 Gate。

### 4.2 子框架注册机制（框架吸收器）

你的要求②"新框架可成为子分析框架"——需要一个注册表：

```
methodology/framework_registry.json
[
  {
    "id": "bottleneck_engine",
    "名称": "瓶颈引擎",
    "适用条件": {"行业": ["制造","半导体"], "数据": "有产业链数据", "问题": "卡点分析"},
    "映射SAC": ["产业链联动", "利润池"],
    "注入方式": "compute.tool_modules.bottleneck",
    "已用次数": 3, "平均Gate分": 0.92, "效果评分": "高"
  },
  {
    "id": "ma_valuation",
    "名称": "并购估值",
    "适用条件": {"行业": "整合期", "数据": "有并购案例库", "问题": "终局判断"},
    ...
  }
]
```

**吸收流程**（复用 `skill-forge` + `absorb_knowledge_base.py`）：
1. 你说"有个新框架" → 提炼为方法文档（适用条件/映射SAC/注入方式）
2. 注册进 `framework_registry.json`
3. 可被分析方案规划器选择
4. 用过的框架自动积累效果数据 → 规划器越用越准

**已有的子框架雏形**（可整理入注册表）：瓶颈引擎、并购估值模块、预测闭环、2hao-deep-research、情景分析、弹性分析、信号链。

### 4.4 元认知反思闭环（事后）

报告完成后，`method_reflection` 记录：
- 实际用了哪些框架、Gate 分数、哪些维度数据不足
- 结论：这个标的+这个框架组合效果如何 → 更新 registry 的效果字段
