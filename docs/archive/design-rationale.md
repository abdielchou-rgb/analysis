# 第一性原理 Brainstorm & Convergence：智能化分析师写作系统

> 这不是 V50 的小修小补。是回到"智能化分析师写作系统"这个根本命题，重推需求、架构和变现路径。

---

## 零、第一性原理锚点

先锁死三句不可动摇的事实：

**F1：系统产出的是文本，不是判断。** 判断来自分析师。系统的职责是让这份文本具备"顶级分析师写出来"的质量——结构、逻辑、风格、说服力。不是替分析师做判断。

**F2：分析师的工作流是"想→验证→写→改"，不是"写→查"。** 当前架构花 2/3 工程力量在 T3 事后检查。但好的写作系统应该在"写"这一步就防止问题发生，而不是写完了再抓。

**F3：系统的竞争壁垒不是模型能力——是方法论+风格库+修改学习。** LLM 谁都能调 API。但一个积累了 200 家机构表达 DNA 的 Bluebook、一个学习了 10,000 次分析师修改偏好的"修改引擎"——别人三年追不上。

# 第一幕：Brainstorm——12 条优化方向

---

## 方向一：架构重组 T2——把"谋篇"和"行文"变成两个独立子系统

### 现状问题
T2 当前是"三阶段：谋篇→行文→精修"，但三个阶段共享上下文、共享 LLM 调用、共享同一个 prompt 模板体系。谋篇输出的 Writing Scaffold 是 JSON，但到了行文阶段，这个 JSON 只是被"塞进 prompt 里让 LLM 参考"——不是作为确定性约束被执行。

### 优化方案

**把 T2 拆成两个独立子系统：**

```
T2a 论证引擎（Argument Engine）—— 零 LLM
T2b 行文引擎（Prose Engine）—— LLM 但高度约束
```

**T2a 论证引擎（零 LLM，确定性）**：

输入：Writing Brief + Knowledge Package
输出：Argument Scaffold（结构化论证骨架）

```python
class ArgumentScaffold(BaseModel):
    """不是 JSON blob——是经过类型和约束检查的论证结构"""
    sections: list[Section]
    
class Section(BaseModel):
    id: str
    type: Literal["judgment", "evidence", "counter", "transition"]
    thesis: str                      # 主题句（一段只一句话）
    evidence_ids: list[str]          # 只引用 T1 中已有的证据 ID
    counter_evidence_ids: list[str]  # 反方证据，非可选
    required_citations: int          # 这段至少引用几个来源
    style_rules: list[str]           # 来自 style_profile 的该节约束
```

**关键变化**：
- T2a 不生成文本。只生成"这段写什么判断、引用什么证据、遵守什么风格约束"
- T2b 拿到 ArgumentScaffold，每一段是独立的 LLM 调用
- T2b 的 prompt 自包含：这段的 thesis + evidence + style_rule → 输出一段文本
- 一段生成失败不影响其他段
- 修改时，分析师说"第三段不对"→ 只重写第三段，不是整节

**T3 的连锁变化**：
- SAC Gate 从"事后检查关键词"变为"直接验证 ArgumentScaffold 的字段完整性"
- 因为 T2a 输出了结构化的 `evidence_ids`，SAC Gate 可以检查"evidence_min: 3"是否满足——根本不需要从文本里找
- Turing Gate 从"全文检查"降级为"逐段检查"——发现一段 AI 腔，只标记这一段

## 方向二：修改引擎——从"整段重写"到"分类手术"

### 现状问题
分析师说"这里不对"，系统不会追问"哪种不对"。默认动作是整段重写——解决了旧问题，可能引入新问题。每一次修改反馈丢失，系统不学习。

### 优化方案

**建立"修改分类法"，嵌入式架构设计：**

```
分析师反馈 → 分类器（确定"不对"的类型） → 定位器（找到文本位置） → 执行器（执行对应修改）
```

**六种"不对"及对应修改动作**：

| 类型 | 检测方式 | 修改动作 | LLM 参与 |
|------|---------|---------|---------|
| 证据弱 | "根据不够"→ 回查 T1, 找更强证据 | 替换证据来源 + 重写该句 | 仅证据句 |
| 判断偏 | "结论太激进/太保守" | 调整判断词强度，不是重写整段 | 仅判断句 |
| 逻辑跳 | "这里缺一步" | 定位断裂点 + 生成中间推理 | 生成新句 |
| 风格错 | "这不是我们家的写法" | 对照 style_profile 做句式替换 | 仅句式 |
| 结构乱 | "这段放错了位置" | 移动段落 + 调整过渡句 | 无（规则驱动） |
| 冗余 | "太啰嗦" | 段落压缩（提取 thesis + 保留证据） | 段落级 |

**修改学习回路**（GH-LK 和 BIG4 共同关注的核心问题）：

每次分类修改后，记录：
```yaml
case_id: "mt_20260722_003"
report_type: "earnings_notes"
analyst_id: "zsw"
original_text: "...直销占比有望突破50%..."
correction_type: "judgment_too_bullish"
correction_action: "有望突破 → 具备突破条件，但需观察"
persisted: true
# 下次同类场景：系统在生成"判断句"时自动降一档措辞强度
```

这项能力一旦建立 1,000+ case，就是系统最深的护城河。
市场上没有第二个写作系统能说"我记录了 1,000 次分析师修改偏好"。

## 方向三：Style-as-Compiler —— 从"风格建议"到"风格编译"

### 现状问题
当前 style_profile 是 YAML 配置文件，被 T2 的 LLM prompt 引用为"请按照这个风格写"。这是建议，不是约束。LLM 可以选择遵守与否。

### 优化方案

**把风格从"prompt 参数"变成"后处理编译步骤"：**

```
LLM 生成原始文本 → Style Compiler 根据 profile 改写 → 输出
```

Style Compiler 是确定性代码（规则引擎 + NLP 工具），不是 LLM：

| 风格特征 | 实现方式 |
|---------|---------|
| 结论先行 | 句子重排序：检测"证据→判断"模式 → 翻转 |
| 判断密度 ≥ 1.0 | 检测每 100 字判断句数 → 不足时从事实句中提取隐含判断 |
| 禁用套话 | 正则匹配 + 替换库（"值得注意的是"→ 删除） |
| 句式长度 | 过长的自动拆分，过短的合并 |
| 术语偏好 | 替换表驱动（"预计"→ 特定机构版本的对应词） |

**好处**：
- Style Compiler 的每个规则都是可测试的——写单元测试，不用"请 LLM 判断风格像不像"
- 一个规则改了，影响已知、可控、可回测
- 机构可以自定义 style profile——不需要懂 prompt engineering，只需要提供替换表和长度偏好

**Turing Gate 的变化**：
- 不再需要"判断 AI 痕迹"——因为 Style Compiler 已经把所有"AI 腔"替换掉了
- Turing Gate 从"检测器"降级为"Style Compiler 未覆盖项的告警器"

## 方向四：T3 瘦身——从事后检查到设计保证

### 现状问题
T3 是 V50 中代码量最大的层。三个门（SAC Gate + Turing Gate + 版本记录）覆盖了大量用"更好的 T2 设计"可以根本避免的问题。

### 优化方案

**T3 缩编为两层：**

```
T3a 维度验证（轻量）
  - 确认 ArgumentScaffold 覆盖了 SAC 的全部 required_dimensions
  - 确认每个 section.evidence_ids 满足 min_citations
  - 确认没有禁止项（内部方法论关键词）
  全部是结构化数据检查，不需要 NLP，不需要 LLM

T3b 版本记录（精简）
  - 记录每次生成的文本版本
  - 记录每次修改的类型 + 位置 + 修改前后 diff
  - 记录输入数据源的快照（T1 计算结果的 hash）
```

**被移除**：
- Turing Gate 检测 AI 痕跡 → 被 Style Compiler（方向三）替代
- 圆桌审计附件 → 作为独立质量监控工具保留，但不阻断交付
- 数值门禁 → 由 T2a 的确定性引用保证（T2 只能引用 T1 计算结果 ID）

**T3 代码量预期缩减：60%**

## 方向五：T0.5 假说验证层——在写之前先想清楚

### 现状问题
分析师常带着模糊的判断进入系统——"我怀疑茅台直销占比能突破50%"。当前架构没有提供一个"帮我验证这个假说"的中间步骤。分析师只能选择：要么直接写（可能写出来发现判断站不住脚），要么自己先去做研究。

### 优化方案

**新增 T0.5 假说验证层——Interactive Mode 的核心**：

```
输入：一个具体的投资假说（非结构化文本）
  "茅台直销占比能突破50%"
  
输出：假说验证报告（300-500 字）
  1. 现有证据支持这个假说（来源 + 等级）
  2. 现有证据反对这个假说（来源 + 等级）
  3. 数据缺口（回答这个假说还需要什么数据）
  4. 类似案例（历史上类似的公司/行业发生了类似的什么）
  5. 建议置信度（基于系统已有的证据覆盖）
```

**这不是"分析系统在做分析"——这是"写作系统在帮分析师理清素材"。**
写报告的前提是想清楚写什么。T0.5 不产生任何报告文本，只产生一张"假说地图"。

**产品形态**：
- 分析师输入框（"验证一个想法"）
- 系统返回假说验证报告
- 分析师基于此决定：写不写？修正假说？放弃？

**与 V50 当前架构的关系**：
- T0.5 调用 T1 的数据引擎和计算引擎（已有能力）
- T0.5 的输出不进入 T2——进入 T0（修正 Writing Brief）
- 不需要新的 LLM 调用——结构化数据呈现，LLM 只用于"类似案例"搜索

## 方向六：插件架构——核心/插件分离

### 现状问题
PKU-C 指出了标准化 vs 定制化的根本矛盾。每个券商要自己的 SAC、自己的风格、自己的数据源。V50 把所有东西放在一个代码库里，每次定制都要动核心代码。

### 优化方案

```
v50_core/
  validate/       # 验证引擎（方向四）
  compile/        # Style Compiler（方向三）
  schema/         # 基础类型系统（T2a 的 ArgumentScaffold 等）
  export/         # 导出器
  plugin_sdk/     # 插件开发工具包

v50_plugins/      # 官方/社区插件
  sac_cicc/        # 中金专属 SAC
  style_guosen/    # 国信风格
  data_wind/       # Wind 数据源适配器
  data_choice/     # 东方财富数据源适配器

  # 用户级自定义（不需要动代码）
  ~/.v50/plugins/
    my_custom_sac.yaml     # 用户自己定义的 SAC
    my_team_style.yaml     # 团队风格覆盖
```

**设计师原则**：
- 核心系统的每次改动必须有版本号和测试
- 插件只提供 YAML/配置——不需懂 Python
- 插件可以 override 核心行为，但不能修改核心代码
- 插件市场——社区贡献可选的 SAC、风格、数据源

## 方向七：可观测性内置——不是横切关注点，是基础设施

### 现状问题
GH-K8s 说得对——0 日志、0 指标、0 追踪。系统改进缺乏数据依据。

### 优化方案

**三项最低可行可观测性**：

**① LLM 调用日志（每次记录）**：
```yaml
timestamp: 2026-07-22T14:30:00+08:00
module: "T2b_prose_engine"
section_id: "sec_03"
prompt_tokens: 2847
completion_tokens: 892
model: "claude-3.5-sonnet"
status: "success"
style_profile: "cicc"
```

**② validate 历史库（SQLite，每次记录）**：
```yaml
timestamp: ...
report_id: "..."
sac_coverage: {dimensions_covered: 5, dimensions_required: 5, ...}
sentence_judgment_density: 1.4
style_deviation_score: 0.12
modification_count: 3  # 从初稿到终稿的修改次数
generation_duration_seconds: 347
```

**③ 修改学习库（SQLite，方向二的持久化）**：
每条修改记录都是一个 case——构成系统学习的基础数据集。

## 方向八：Interactive Mode 原型——问答 > 报告

### 现状问题
系统只有 Batch Mode（输入→等待→输出）。分析师真实工作流需要"先问一个问题，根据答案决定下一个问题"。

### 优化方案

**最低可行交互模式（基于 T1 数据引擎）**：

```
分析师输入： "茅台直销占比现在多少？"
系统返回：   "2024H1 直销占比 42%，去年同期 38%。同比提升 4pct。行业平均 28%（五粮液）"

分析师追问： "那毛利率呢？直销 vs 批发的毛利率差异？"
系统返回：   "直销毛利率 94.5%，批发毛利率 89.3%。直销比批发高 5.2pct。当前直销占 42%→如果到 50%，毛利率预计提升 0.5pct"

分析师追问： "市场怎么看？一致预期是什么？"
系统返回：   "一致预期 2024 年直销占比 45%（Bloomberg 12 家覆盖），超过 45% 的只有 2 家。市场分歧点在..."
```

**架构实现**：
- 不需要新的数据引擎——T1 已有的计算能力
- 只需要一个新的 UI 层 + 对话状态管理
- 每个问题是一个独立的 T1 查询，不是 LLM 对话
- LLM 只用于"把查询结果转化为一句话回答"

## 关键架构决策总结

| 决策 | V50 当前 | 优化方向 | 理由 |
|------|---------|---------|------|
| T2 的核心 | LLM 三段式（谋篇/行文/精修） | 论证引擎（确定性）+ 行文引擎（LLM 约束） | 错误不传播，修改可定位，T3 瘦身 |
| 风格控制 | prompt 参数（建议） | Style Compiler（强制） | 可测试、可控、可定制 |
| 质量保证 | T3 事后检查（2/3 工程量） | T2 设计保证 + 轻量 T3 | 事后检查永远赶不上设计保证 |
| 修改方式 | 整段重写 | 分类修改 + 修改学习 | 唯一能做深的学习回路 |
| 分析师入口 | "写一份报告" | "先问一个问题" + "再写报告" | 匹配真实工作流 |
| 数据需求 | 深度精确 | 广度覆盖 + 缺口标识 | 写作系统不需要做计算，需要做叙事 |
| 架构形态 | 单体 | 核心+插件 | 定制化 scalable 的唯一路径 |

## 一个简单的验证

拿"茅台直销占比能否突破 50%"为用例，对比新旧架构的工作流：

**V50 当前**：
1. 分析师写 Writing Brief → 核心判断"看多，直销占比突破 50%"
2. T1 计算财务数据
3. T2 谋篇→行文→精修 → 20,000 字报告
4. T3 门禁检查 → 通过 → 交付
5. 《分析师发现数据支撑不够强，但报告已经生成了》

**优化后的工作流**：
1. 分析师在 T0.5 输入假说："直销占比突破 50%"
2. 系统返回假说验证报告：
   - 支持证据（3 条，来自年报/渠道数据）
   - 反对证据（2 条，来自一致预期/同行对比）
   - 数据缺口（渠道库存精确数据未公开）
   - 类似案例（五粮液 2019 渠道改革的三个阶段）
3. 分析师看到缺口，修正判断："需要进一步调研渠道库存"
4. 修正 Writing Brief → 加入"渠道库存数据待核实"标记
5. T2a 生成 ArgumentScaffold → 证据缺口处标记 "estimates"
6. T2b 逐段生成 → 缺口段生成 "data pending" 标注
7. Style Compiler 调整措辞 → 中金风格
8. 交付 → 分析师确认

**关键区别**：第 2 步花 30 秒，避免了第 3-5 步做无用功。

## 一句话总结

> **V50 当前是在"让 AI 写报告"上做质量控制。优化方案是把控制提前——让"写报告"的每一步都被结构化约束，让 LLM 只在"写成句子"这一步出现，让每次修改都变成系统能力的增量。**
