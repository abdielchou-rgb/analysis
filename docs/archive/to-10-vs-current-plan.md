# 距离满分还差什么？

坦率地说：**不能。** 我选的三件事能把分数从现在的 ~5-7 分推到 ~7-8 分，但到 10 分还差一个量级。

我的第一次收敛有一个根本性的盲点：**我把"信任"简化成了数据可追溯 + 风格 + 洞见三个维度——但信任的真正基础是"可验证的历史表现"。**

让我重新审视这个问题。

---

## 一、每个角色的"10分"到底长什么样

### P1（摩根士丹利）：10分 = 可以直接发给客户，不做任何编辑

| 维度 | 7分 | 10分 |
|------|-----|------|
| 数据 | 有血统标注、有时效性水印 | **市场校准：WACC 不是来自历史模型，来自当前 Bloomberg 数据** |
| 叙事 | 结构完整，信息密度高 | **选择性：知道什么该省略，每页只讲一个核心故事** |
| 信心 | 标注置信度 | **能说"这是我们最有信心的判断"——因为它知道自己的历史准确率** |

**7分到10分的差距**：不是功能问题，是"这个系统的判断我买不买账"的问题。

### P2（麦肯锡）：10分 = 我愿意为这个洞见向客户收费

| 维度 | 7分 | 10分 |
|------|-----|------|
| 洞见 | So What 规则引擎，覆盖 20 种常见模式 | **创造了我不曾想到的分析角度——规则引擎做不到** |
| 归因 | 解释假设处于 P85 的原因 | **追溯同类公司在 P85 假设下的实际结果——正反馈还是负反馈？** |
| 原创性 | 有结构的分析 | **有观点的分析** |

**7分到10分的差距**：InsightCompiler 再完善也只是规则引擎，规则引擎不能创造新分析框架。10 分需要系统有自己的分析创新。

### P3（中金）：10分 = 团队能用它承接 50% 以上的报告工作量

| 维度 | 7分 | 10分 |
|------|-----|------|
| 风格 | 配置化的 writing DNA，够像中金的人写的 | **能无缝嵌入团队的工作流——草稿 -> 组内审 -> 终稿，而非一次生成** |
| 合规 | P0 检测 + 合规检查 | **合规检查是自动触发的，不是一个独立步骤** |
| 价值 | 系统写初稿，人改 | **系统从人的修改中学习——同一类错误不会出现第二次** |

**7分到10分的差距**：不是输出质量，是工作流集成和学习能力。

### P4（德勤）：10分 = 在受监管环境中放心使用

| 维度 | 7分 | 10分 |
|------|-----|------|
| 血统 | 每条数据可追溯到来源文件/单元格 | **数据血统是自动生成的，不是事后标注的——extraction -> provenance 在同一步完成** |
| 审计 | 记录了提取时间和来源 | **有完整版本历史——谁在什么时候基于什么数据修改了什么假设** |
| 责任 | 标注了置信度 | **有明确的错误率基准和人类复核门槛** |

**7分到10分的差距**：需要从"设计上可审计"到"运营上可审计"——这需要版本控制和工作流。

## 二、我上次遗漏的三个结构性缺口

回头看，我的三个建议（数据血统+置信度、风格DNA、So What层）解决的是**一份报告的静态质量**。但满分要求的是**一个服务机构的信任闭环**——系统要证明自己不是一次写得好，而是可以持续交付高质量、不断学习、且风险可控。

要闭环，需要三块我上次没纳入的东西：

### 缺口 1：预测回路（Prediction Loop）

**问题**：所有评分者都说"凭什么相信这个概率？"——而我给的答案是改输出格式（加置信度标注）。这是回避问题。真正的问题是：**系统从来没有追踪过自己的预测准确率。**

当前，Conviction Matrix 输出 "base_prob=55%, bull=20%, bear=25%"，但：
- 一个月后，这个股票的走势验证了这个概率分配吗？
- 一年后，系统的 bull/bear 判断准确率是多少？
- 在哪些行业、哪些假设类型上系统最容易出错？

**没有这些数据，任何关于"可信度"的修饰都是空话。**

**需要做的**：
- 每条预测记录带唯一 ID，关联到后续结果
- 定期生成 Prediction Audit Report（预测准确率、校准曲线、误差归因）
- 用历史准确率自动调整 Conviction 概率（如果系统历史上偏乐观，自动下调 bullishness）

### 缺口 2：协作工作流（Collaborative Workflow）

**问题**：所有专业服务机构的报告生产都是多轮迭代的。草稿 -> 组内 Review -> 修改 -> 合规审核 -> 终稿。当前系统是"一次生成"——没有草稿状态、没有版本对比、没有修改学习。

P3 说的是"我的团队怎么用"——如果系统生成一份报告，分析师改了三版，**系统不能从这三次修改中学到任何东西**，那就只是一台打印机，不是一个协作工具。

**需要做的**：
- Report draft versioning（草稿/初审/终稿状态管理）
- Edit diff tracking（对比两版差异 + 自动提取修改模式）
- 从人类修改中学习（如果人类每次都把"我们预计"改成"我们判断"，系统应自动调整 writing DNA）

### 缺口 3：责任边界（Liability Boundary）

**问题**：这不是技术问题，但可能是商业化的最大障碍。P4 的审计追问最终指向：**系统出错时，责任落在谁身上？**

- 如果系统输出有误，用户没发现就直接用了——谁的责任？
- 如果用户修改了系统的输出但保留了系统的结构和数据——谁的责任？
- 如果系统标注了"此假设置信度低"但用户还是用了——谁的责任？

**需要做的**：
- 在输出中明确标注"生成边界"（哪些部分是系统自信的，哪些部分需要人工复核）
- 版本水印：系统生成的每一版都可以唯一标识（防止修改后冒用）
- 建立人类复核 checkpoint 标准（什么条件下必须有人类签字）

## 三、修正后的完整路线图

现在我可以重新排一个更诚实的优先级：

```
Phase 1: 数据层夯实（2-3 周）
  P0: 数据血统 + 置信度感知输出 ✅（已规划）
  Batch extract 修复（模板检测、目标 PE 提取）

Phase 2: 身份与风格（1-2 周）
  P1: 风格 DNA 可配置化 ✅（已规划）

Phase 3: 洞见层（3-4 周）
  P2: InsightCompiler + So What 层 ✅（已规划）

Phase 4: 信任闭环（4-6 周）← 我上次遗漏的核心
  P3: 预测回路 —— 预测记录 + 准确率追踪 + 自动校准
  P4: 协作工作流 —— Draft/Review/Final 三态 + Edit diff + 从修改中学习

Phase 5: 市场级部署（持续）
  P5: 责任边界 —— 版本水印 + 复核 checkpoint + 错误率公开基准
```

### 按评分者的预估提升

| 评分者 | 当前 | Phase 1-3 后 | Phase 4-5 后 |
|--------|------|-------------|-------------|
| P1（MS） | 6/10 | 7.5/10 | 9/10 |
| P2（McK） | 7/10 | 8/10 | 8.5/10 |
| P3（CICC） | 5/10 | 7/10 | 9.5/10 |
| P4（Deloitte） | 4/10 | 6/10 | 9/10 |

Phase 4（预测回路）最直接地拉高 P1 和 P4 的分数——因为他们最关心"这系统到底靠不靠谱"。Phase 4（协作工作流）最直接拉高 P3 的分数——因为他关心"我的团队怎么用"。

**P2 的分数最难拉。** 即使所有基础做完了，洞见的原创性上限在于系统的推理能力，而这是当前架构（纯规则引擎）的瓶颈。要让 P2 打到 9/10，可能需要引入更灵活的推理机制——这不是短期内能靠工程解决的事情。

## 四、我自己的复盘

我上次的收敛遗漏了一个关键区分：

**我把"系统能不能写一份好报告"和"系统能不能成为一个可信赖的合作伙伴"混在一起了。**

我选的三个建议（P0/P1/P2）都在回答第一个问题。而我对评分的分析（看评分者反馈）本应该告诉我——他们在问的是第二个问题：

- P1 说的"我敢不敢发给客户"——不是问报告质量，是问 trust
- P2 说的"我愿不愿意为这个洞见收费"——不是问输出结构，是问 originality
- P3 说的"我的团队能否用它"——不是问风格像不像，是问 integration
- P4 说的"我能不能签审计意见"——不是问数据对不对，是问 accountability

**如果重来一次，我应该在 16 个建议中筛出 4 个而不是 3 个。** 除了我选的 P0/P1/P2，应该再加上 P3（预测回路）作为必要项。因为预测回路是所有"信任"问题的基础——没有它，P0 的置信度标注没有校准依据，P1 的风格没有错题集来迭代，P2 的 So What 没有历史数据来验证。

**一句话：满分需要的不只是让系统写得更像人，而是让系统证明自己值得被信任。这两者之间差了一个预测回路。**
