## 一、总评

**我们做了"让管线不死"，还没做"让管线更快"。**

本轮落地的 P0-1a/P0-2a/P0-3 是**止血措施**：给 research_planner 加 30s 独立超时、给三个确定性节点加墙钟预算、补段级观测日志。这些是必要的——没有它们，管线会因单个慢节点挂死整条链。

但这不是加速。管线的绝对瓶颈（LLM 写作占 44-74%）没有被触碰。我们做的三件事，用审计的原话说："方向对、事实基本准、但手术刀不够细"。

## 二、已落地 vs 业界最优 vs 审计盲区

### 2.1 已落地（3 项）

| 编号 | 改动 | 实际效果 | 局限 |
|---|---|---|---|

### 2.2 未做但业界在做的（按杠杆率排序）

| 优先级 | 方案 | 原理 | 预估效果 | 实现难度 |
|---|---|---|---|---|
| **P0** | 单次 HTTP 超时分级 | research 30s / 组写作 60-90s / merge 45s（替代全局 180s） | 重尾直接砍 50-70% | 低（改 3 个调用点） |
| **P0** | 僵尸线程治理 | 单次调用短超时 + `thread.interrupt_main()` 或 provider 级熔断计数 | 消除"熔断后仍在燃烧"的隐性负载 | 中 |

## 三、三处审计指出但未落地的代码级刀口

### 3.1 单次 HTTP 超时 180s 是重尾的最直接放大器

**证据**：`deepseek_client.py` 每个 provider 尝试超时 = `llm_http_timeout()` 默认 **180s**（openrouter 流式更被 `max(180, 300)` 抬高到 300s）；失败后走全量回退链再打一轮。8 组并发 × 2 次 attempt × 多 provider 回退 = write_sections 的 2502s 不需要任何"慢模型"，仅超时叠加就够。

**审计原文**：

> 这比"全局墙钟预算"更便宜、先手更靠前：
> - 对 research_planner / 规划类短任务单独设 30s 超时；
> - 对组写作把超时从 180s 收到 60-90s 并在超时后快速降级到备用 provider；
> - 对 merge（串行、单次调用）单独设超时档。

**当前状态**：P0-1a 只改了 research_planner 的 30s。组写作和 merge 仍是 180s。

### 3.2 merge 与自愈/重试成本没进收益模型

**证据**：`_write_group` 全部失败后有一段串行 SELF-HEAL（换 provider 全组重写），再统一走 `_editor_merge`（DeepSeek 读全部组输出，超过 `EDITOR_LLM_MERGE_MAX_CHARS=50_000` 时还要分桶两段合并）。这两个都是 node 级耗时的一部分。

**审计原文**：

> P0-2 若只读现有日志，会得到"某个组 40s 最慢"，但无法区分 107s 里有多少是：
> - 正常组写作墙钟（≈ 最慢组）；
> - 失败组的 SELF-HEAL 串行重写；
> - merge 的 1-2 次 LLM 调用。

**当前状态**：P0-2a 加了 SELF-HEAL 和 merge 的段级日志。但"拿到最慢组之后干什么"的第二刀没落地。

### 3.3 僵尸 LLM 线程

**证据**：`question_tree_v2` 用 6 路线程池，主线程 `wait(...timeout=剩余预算)`，预算耗尽即 break 并 `pool.shutdown(wait=False, cancel_futures=True)`。问题：**`cancel_futures` 只能取消尚未开始的 future；已经在 `_llm_generate_questions` 里发起 `requests.post(timeout=180s)` 的线程无法被中断**（Python 线程不可杀）。

**审计原文**：

> 45s 预算只保证主流程 45s 脱身；被留下的慢线程仍可能再占用 100-200s，继续消费 provider 限流窗口与队列。
> 该节点结束后，AgentGraph 随即进入同一层的其它节点（含后续 write_sections 的 6-8 组并发写作）。僵尸请求与组写作并发打同一 provider，正是原 PROFILE 里 429 连锁失败的复现温床。

**当前状态**：P0-1a 给单次调用加了 30s 超时（比 180s 好很多），但僵尸线程本身的善后（回退计数 + provider 限流窗口感知）未做。

## 四、我们与"全网最优"的真实差距

### 4.1 业界对标

| 指标 | 二号分析师（当前） | 顶级投行研报系统 | 差距 |
|---|---|---|---|
| 单份报告时间 | 5-15 min | 1-3 min（人工+工具） | 2-5x |
| LLM 调用次数 | 20-50 次 | 5-15 次 | 2-3x |
| Prompt token 量 | 8-12K/维度 | 2-4K/维度 | 2-3x |
| 重试轮数 | 1.5-2 轮 | 0-1 轮 | 1.5-2x |
| 数据采集 | 30-60s | 5-15s（缓存） | 2-4x |

### 4.2 最大差距在哪

**Prompt token 量**（8-12K vs 2-4K）——这是 LLM 延迟的根因。每多 1K token，LLM 处理时间多 1-3s。8 个组 × 3 段 × 3 维度 = 72 次 LLM 调用，每次多 2-6s = 全管线多 144-432s。

**解法是"按维度动态注入"**：维度 1（商业模式）不需要 DCF 敏感性矩阵；维度 5（估值）不需要竞争格局表格。按维度切片子集，8K→2K。

### 4.3 一句话

> **最大杠杆是"按维度动态注入 prompt"—— 把 8-12K token 的全量注入压缩到 2-4K，LLM 处理时间直接砍半。其次是"单次超时分级（180s→30/60/90s）"—— 零质量损失的重尾裁剪。两者组合可将管线从 ~270s 降到 ~100-130s（降幅 52-63%）。**

## 五、推荐执行路线（审计修正版）

```
第一刀（确定性、零风险）：
  单次 HTTP 超时分级（180s → research 30s / 组写作 60-90s / merge 45s）
  → 重尾直接砍，不改 prompt、不改逻辑

第二刀（观测闭环）：
  merge 自愈段级日志 + 僵尸线程回退计数
  → 拿到数据再决定下一刀

第三刀（最大杠杆）：
  按维度动态注入 prompt（8K→2K）
  → LLM 延迟砍半，但需要 KB 门禁稳定后才能做

第四刀（条件性）：
  Gate 反馈维度化 → 省 1-2 轮全量重写
  Provider 实时路由 → 省 fallback 等待
```

---

## 六、一句话结论

> **我们做了止血，还没做加速。审计的刀口比我们更准：先砍单次超时（180s→30/60/90s），再补 merge/自愈段级观测，最后做按维度动态注入。前两刀确定性、零风险、不改语义；第三刀是最大杠杆但需要 KB 门禁稳定。全网最优不是某一个方案，而是"先止血→再观测→再压缩→再路由"的四步闭环。我们现在在第一步和第二步之间。**
