# 2号分析师排版问题与管线执行慢——根因诊断 + 顶级打法

> 两个"为什么总是出现"的系统性问题
> 日期：2026-08-06

---

## 第一部分：为什么总是出现？

### A. 排版问题为何反复复发

| 复发点 | 表象 | 根因 |
|--------|------|------|
| docx 空段落/空白页 | R40 修过（16%→修复），R79 又出现（16%+55连续空段） | 每次是"改了导出路径就复发"，从未固化到**唯一出口** |
| 图表堆附录 | R78 升 error 级，重做报告又图表随文 OK 但 PDF 无图 | 多套导出并行（LibreOffice/pandoc/reportlab/Word COM），各路径行为不一 |
| 排版检查"能拦但不拦" | layout_quality warning 级，Gate 只看 error | 检查项 severity 与影响不匹配（排版是 P0 但设 warning） |

**根因本质：排版问题不是"代码 bug"，是"没有唯一渲染管线"。**

- 报告文本是 Markdown → 多套工具各自转 DOCX/PDF（pandoc、LibreOffice、reportlab、python-docx）
- 每套工具对空段/图片/字体的处理不同 → 同一份 MD 转出不同质量的 DOCX/PDF
- 环境依赖缺失（LibreOffice 没装）→ 静默降级 → 无图 PDF 照样"成功"
- 修好一条路径（如 python-docx），另一条路径（如 pandoc）又出问题 → 打地鼠

**关键认知**：真实机构（高盛/中金）排版是**模板驱动 + 唯一渲染器**——MD 是中间产物，最终 DOCX/PDF 由一套引擎 + 统一模板产出，不存在多路径分叉。

### B. 管线执行慢为何总是出现

| 慢点 | 表象 | 根因 |
|------|------|------|
| 写改循环 | 3 轮 Gate 打回 → 全量重写 → 40+ 分钟 | 每轮重新掷骰子，无收敛保障（R7/R8 部分缓解） |
| LLM 调用 | 每个 section 一次调用，6-10 段串行 | 分段串行生成，未并行化 |
| Gate 迭代 | 打回 → 重写 → 再查，循环 | **生成端不约束，靠事后检查打回**，每轮全量重跑 |
| 数据采集 | 网络采集慢（akshare/Tavily） | 每次重跑重新采集，无缓存命中 |

**根因本质：管线慢 = "迭代式试错"而非"一次写对"。**

- LLM 生成"初稿" → Gate 发现 N 个问题 → 打回全量重写 → 重写引入新问题 → 再打回
- 每轮都是**全量重写**（不是局部修订），成本随轮次线性上升
- 慢的根源不是单次调用慢，而是**迭代轮次多 + 每轮全量**的乘法效应

**关键认知**：顶级机构的报告不是"生成→检查→打回"循环，而是"强约束生成→一次整合→终审"。迭代轮次趋近 1，而不是 3-5。

## 第二部分：顶级打法

### A. 排版问题的顶级打法

#### 打法 A1：唯一渲染管线 + 模板驱动（根治）

**对标**：高盛/中金/麦肯锡的报告排版是**模板 + 单一渲染器**。

- MD 只是中间层，最终 DOCX/PDF 由**一套引擎**（推荐 pandoc → 统一 docx 模板，或 LibreOffice headless → 统一模板）产出
- 全项目只允许一条导出路径，其他路径删除或显式报错
- 模板定义：字体/标题层级/段落间距/页边距/图表位置，一次定义全报告生效

**落地**：
```bash
# 唯一出口：pandoc + 统一参考模板
pandoc report.md -o report.docx --reference-doc=templates/cicc_template.docx
# LibreOffice headless 转 PDF（含图）
soffice --headless --convert-to pdf report.docx
```

#### 打法 A2：排版质量内建（不是事后检查）

**对标**：CI/CD 的"格式化内建"（prettier/black）。

- **生成端约束**：section_writer prompt 明确"段落之间空一行，禁止连续空行；图表必须随文；表格用标准格式"
- **中间产物校验**：MD 生成后立即校验（空段/图表位置），不合格**在写入前**拦截，而非导出后
- **导出产物验证**：DOCX 导出后自动跑 VisualGate（空段率/图表嵌入/字体），不合格阻断

**落地**：
```
MD 生成 → MD 校验（空段/图随文）→ 通过才导出
导出 DOCX → VisualGate 产物验证 → 通过才交付
```

#### 打法 A3：渲染环境容器化

**对标**：Docker 锁定渲染环境。

- 用 Docker 镜像固定 LibreOffice + pandoc + 字体（SimHei/宋体）+ 依赖版本
- 任何机器渲染结果一致，杜绝"这台机器有图那台没图"

### B. 管线执行慢的顶级打法

#### 打法 B1：一次写对（First-time-right）——治本

**对标**：麦肯锡/高盛"初稿即近终稿"。

- **生成端强约束**：把 Gate 的检查项变成 prompt 的写作约束（反方三段式/数据带依据/图表随文/无模板句），让 LLM **一开始就写对**
- 目标：把写改循环从 3-5 轮压到 **1-2 轮**

**落地**：
```
改造前：LLM写 → Gate查N问题 → 全量重写 → 再查
改造后：强约束prompt写 → 局部修订小问题 → 终审
```

#### 打法 B2：局部修订而非全量重写

**对标**：diff-based 代码评审，而不是"重写整个文件"。

- `_locate_failed_segments` 已有（R66），能定位失败段
- **升级**：失败时只重写失败段（组级局部重写），不是全量重写
- 配合 checkpoint（R78）：中断续跑不重头

**落地**：
```
Gate 失败 → 定位失败段（template_repeat 在第3段）→ 只重写第3段 → 再查
```

#### 打法 B3：LLM 并行化 + 结果合并

**对标**：多 agent 并行研究（AutoGen/CrewAI）。

- 多个 section 并行生成（互不依赖的段落），最后统一合并
- 已有 `--workers 2`（run_reports），升级到 section 级并行
- **注意**：并行需要解决"全局一致性"（Bold Call/口径），合并时由总编辑统一

**落地**：
```
5 个独立 section 并行生成 → 总编辑合并统一口径 → 终审
```

#### 打法 B4：Prompt Caching 降本提速

**对标**：Anthropic prompt caching / DeepSeek KV cache。

- 系统提示词（SAC 框架 + 注入模块）不变，缓存其 KV
- 数据上下文重复注入时命中缓存，省 80-90% 重复 token 处理时间
- DeepSeek 支持 context caching（自动），确保**系统提示词部分每次相同**

**落地**：
```
系统提示词（框架+注入）→ 保持稳定不变 → 触发缓存
只变的部分（数据/段落）→ 增量处理
```

#### 打法 B5：数据采集缓存 + 增量更新

**对标**：数据仓库的增量 ETL。

- 数据采集结果缓存（R48 已有 `_cached_collected`），**重试轮不重新采集**
- 网络数据（akshare/Tavily）加 TTL 缓存，同一天同标的不重复抓
- 慢的 30-40% 来自数据采集，缓存直接砍掉

#### 打法 B6：并行 Gate 检查 + 快速失败

**对标**：CI 的并行测试 + fail-fast。

- 已有 LLM 检查并行（R15），扩展到**全部检查并行**
- 确定性检查（快）先跑，LLM 检查（慢）并行跑，取最慢为总时长
- 关键：**确定性检查失败立即返回**，不等 LLM 检查（fail-fast）

## 第三部分：落地优先级

### 排版（先做，价值高见效快）

| 优先级 | 打法 | 工作量 |
|--------|------|--------|
| P0 | A1 唯一渲染管线（pandoc+模板） | 1-2天 |
| P0 | A2 生成端排版约束 + MD 写入前校验 | 0.5天 |
| P1 | A3 渲染环境 Docker 化 | 1天 |
| P1 | 修复 LibreOffice → PDF 含图 | 0.5天 |

### 速度（治本，需配合激励整改）

| 优先级 | 打法 | 工作量 |
|--------|------|--------|
| P0 | B1 生成端强约束（一次写对） | 2-3天（配合反方/数据prompt） |
| P0 | B2 局部修订（已有基础，接线） | 1天 |
| P1 | B4 Prompt caching（配置） | 0.5天 |
| P1 | B5 数据缓存（已有基础，补TTL） | 1天 |
| P1 | B3 section 并行 | 2天 |
| P2 | B6 全检查并行 | 1天 |

## 第四部分：核心洞察

**排版问题根因 = 没有唯一渲染管线**（多路径分叉，各路径行为不一）。**慢的根因 = 迭代式试错**（生成端不约束，靠事后打回，每轮全量重写）。

**顶级打法的共性**：
1. 排版：**模板驱动 + 唯一渲染器**，让格式问题一次定义全报告生效
2. 速度：**一次写对 + 局部修订**，把迭代轮次压到 1-2，而不是靠更快的单次调用

一句话：**2hao 排版和慢的问题，本质都是"架构缺唯一性"——渲染没有唯一出口，生成没有一次写对的约束。补齐这两点，两个顽疾同时缓解。**
